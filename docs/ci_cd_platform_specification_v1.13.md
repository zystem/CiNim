# Назначение документа

Документ задает продуктовые, функциональные и архитектурные требования к новой self-hosted CI/CD платформе, работающей только в Kubernetes. Цель --- получить управляемость TeamCity, экосистему и гибкость Jenkins (императивный pipeline-скрипт, расширяемый UI), переносимость pipeline-as-code современных SaaS-систем и Kubernetes-native исполнение без зависимости от конкретного Git-хостинга. Главный приоритет реализации --- малое потребление памяти на сервере, в job Pod и в браузере, а также отсутствие утечек во всех компонентах.

Разработку ведет Claude под руководством владельца продукта. Поэтому документ написан как рабочая спецификация исполнителя: каждое требование имеет стабильный ID и проверяемый критерий, неоднозначные места вынесены в явный список вопросов (раздел 21), а порядок работ задан вертикальными срезами с критериями выхода (раздел 17). Читатели-люди --- владелец продукта, архитекторы, SRE и security --- используют тот же текст для ревью решений.

Рекомендуемый продукт --- набор независимых микросервисов на Nim, объединенных в шарды (cells), которые масштабируются добавлением шардов. Исполнение agentless: каждый шаг pipeline выполняется в отдельном Pod, который создает и наблюдает job-контроллер, а данные передаются через общее storage и env-файл. Pipeline --- императивные скрипты на Lua 5.4 с журналом воспроизведения, состояние хранится в rqlite, протокол между сервисами --- Protobuf, расширения изолированы. Первая версия должна решать CI и управляемый CD; не следует одновременно строить Git-хостинг, артефактный репозиторий и полноценный секрет-менеджер.

# Резюме решения

| **Решение** | **Выбор** |
|:---|:---|
| Развертывание | Только Kubernetes, установка через Helm. Работа вне Kubernetes (Docker Compose, VM, bare metal, shell-агенты) не предусмотрена |
| Язык реализации | Nim 2.x (ORC), статические бинарники; приоритет --- малая память и отсутствие утечек |
| Архитектура | Микросервисы с первого релиза; шард (cell) = набор сервисов с собственным rqlite и контуром логов (два независимых узла VictoriaLogs с агентом vlagent); масштабирование добавлением шардов, тенанты закрепляются за шардом через directory |
| Исполнение | Agentless: постоянных агентов нет; job-контроллер создает Pod на каждый шаг, Pod можно запускать многократно над постоянным томом run; все шаги run подключают общее storage; передача данных через env-файл и файлы |
| Pipeline | Императивный скрипт Lua 5.4 в песочнице; runtime-исполнение как в Jenkins с журналом воспроизведения (replay); YAML не используется |
| Протоколы | Protobuf (proto3) между сервисами и для плагинов; REST/JSON остается внешним API |
| Расширения | Step-плагины --- OCI-образы с файловым Protobuf-контрактом, service-плагины --- отдельные сервисы; capability permissions; подпись; без загрузки кода в процесс сервера; UI-вклад через extension points и изолированные iframe |
| UI | Серверный рендеринг без SPA, постоянная ссылка на любой элемент, минимальный клиентский код и память браузера; логи показываются окном |
| Логи | VictoriaLogs (upstream без форка; два независимых узла, которые питает vlagent) --- хранилище и источник истины логов; роль coordinator и репликация через NATS не нужны; браузер работает только с окном лога, полный лог отдается по кнопке «скачать» потоком |
| Безопасность | OIDC/SAML, RBAC+scopes, Vault/KMS, short-lived credentials, OIDC federation, Lua-песочница, restricted Pod Security, policy engine |
| Совместимость | Импортеры Jenkinsfile, TeamCity Kotlin DSL, GitHub Actions, GitLab CI и Travis/CircleCI, генерирующие Lua-скрипты, с отчетом потерь |

# Как пользоваться документом (для исполнителя)

## Соглашения

- Каждое требование имеет ID вида `PIP-001`, `DAT-002`, `NFR-006`. Требование обязательно, если не помечено `[рекомендация]`. Имя каждого теста содержит ID проверяемого требования.

- Метка `[M0-CHECK]` означает допущение, которое нельзя принимать на веру: его проверяет spike этапа 0 (раздел 17), результат фиксируется в ADR. Пока проверка не выполнена, на допущение нельзя опираться в публичных API.

- Метка `[ОТКРЫТО Q-xx]` отсылает к вопросу из раздела 21, который решает владелец продукта. Исполнитель не выбирает ответ сам: он останавливается, формулирует вопрос и предлагает вариант по умолчанию.

- Метка `[проверить]` в разделе 2 означает утверждение о стороннем продукте, не подтвержденное обзорной страницей официальной документации на дату документа.

## Правила работы

- **E-001 Вертикальные срезы.** Работа идет срезами, каждый из которых проходит весь путь (API, состояние, Pod, UI, тест). Горизонтальные слои без работающего сценария не принимаются.

- **E-002 Тесты первыми.** Для каждого требования сначала пишется тест, затем реализация. Срез закрыт, когда выполнены критерии выхода этапа.

- **E-003 Память как требование.** Любая очередь, буфер, кэш и таблица ограничены по размеру. Каждый C-ресурс (Lua state, TLS-контекст, дескриптор) обернут типом с `=destroy`. Циклические ссылки между `ref`-объектами запрещены без явного обоснования в коде. Те же правила действуют для клиентского кода UI (UI-008).

- **E-004 Наблюдаемость памяти.** Каждый процесс отдает метрики RSS и `getOccupiedMem`, а сборка для CI включает вариант с AddressSanitizer/LeakSanitizer для серверных сервисов, executor и runner shim.

- **E-005 Без чужого кода в control plane.** Пользовательские скрипты и плагины исполняются только в отдельных процессах или Pod с ограничениями (PLG-001, SEC-007).

- **E-006 ADR.** Каждое архитектурное решение и результат `[M0-CHECK]` записывается в `docs/adr/NNNN-название.md`: контекст, варианты, решение, условия пересмотра.

- **E-007 Не выдумывать.** Нельзя придумывать поведение сторонних систем или библиотек. Если факт не подтвержден документацией или экспериментом, он записывается как допущение с меткой `[M0-CHECK]`.

## Рекомендуемая структура репозитория

```text
proto/            # .proto: internal, plugin; проверка совместимости N/N-1
src/api/          # публичный API и UI-сервис (серверный рендеринг)
src/directory/    # каталог шардов: тенант -> шард
src/scheduler/    # очередь, квоты, приоритеты
src/executor/     # pipeline-executor: Lua-песочница, journal, replay
src/jobctl/       # job-контроллер: Pod, storage, secrets, cleanup, watch
src/logs/         # log collector и gateway: прием логов от shim, redaction, отправка в vlagent, модуль контура логов, окна и выгрузка
src/shim/         # runner shim: обертка шага в Pod, env-файл, результат
src/events/       # события, webhooks, schedules
src/cli/          # cicd CLI
src/common/       # общие типы, protobuf-код, клиент Kubernetes, метрики, лимиты памяти
lua/stdlib/       # Lua API v1 (6.7), типовые заглушки для IDE
plugins/          # first-party плагины (по одному каталогу)
deploy/helm/      # чарты сервисов и шарда
docs/adr/         # журнал решений и результаты M0
tests/            # unit, contract, integration, e2e, soak, security
```

**Изменения v1.2.** Работа вне Kubernetes удалена из объема. Агенты, пулы агентов, executors container/shell/VM и режим modular monolith заменены agentless-исполнением в Pod (6.4, 7). Добавлены общее storage и обмен данными между шагами (6.8). Масштабирование переведено на шардирование (7.3), эскалация через PostgreSQL исключена. Логи хранятся в ZincSearch как в источнике истины, окном (DAT-001, DAT-007), требования к резервному копированию логов вынесены в NFR-007. Добавлен бюджет клиентской памяти (UI-008). Вопросы Q-11--Q-15 добавлены или переформулированы, вопрос про адаптер PostgreSQL снят.

**Изменения v1.3.** Учтено, что репликация ZincSearch уже реализована в форке (JetStream, coordinator, бэкапы): исправлено утверждение v1.2 об отсутствии репликации, NATS JetStream включен в состав шарда (D-03, DAT-008, DAT-010, DAT-011, 7.1, 7.3), RPO логов пересчитан (NFR-007). Запуск Pod над постоянным томом сделан явным требованием (RUN-014), добавлены постоянные тома между run (STO-008), раздел 7.4 переписан. Бюджет клиентской памяти ужесточен до heap ≤ 10 MiB и ≤ 5 MiB для логов (UI-008, NFR-016), окно лога уменьшено до 200 строк (DAT-007).

**Изменения v1.4.** Чтение логов упрощено: оно всегда идет с мастера ZincSearch, а отставание в пару секунд признано допустимым (D-20, DAT-011). Из collector убран собственный путь чтения (кольцевой буфер и live fan-out), целевая задержка live tail в NFR-005 повышена до 5 с.

**Изменения v1.5.** Роль coordinator ZincSearch перенесена в платформу (D-21, DAT-010): отдельный coordinator и его дисковый буфер удалены, запись идет напрямую в поток JetStream, состояние узлов, мастера и бэкапов хранится в rqlite шарда. Метрики Prometheus форка (ZF-6) сняты. Контур логов признан частью ядра шарда: его недоступность означает недоступность шарда, деградированного режима нет (SHD-005).

**Изменения v1.6.** Добавлен допуск запуска по состоянию ZincSearch (RUN-015, D-22): при отсутствии мастера или отказе публикации новые step и Pod не запускаются, run остаются в очереди с причиной `logs_unavailable`, а исполняющиеся step не прерываются. Уточнено, что coordinator изначально является частью основного модуля (D-21). Добавлены критерий приемки 26 и вопрос Q-16.

**Изменения v1.7.** Scheduler, log collector и coordinator ZincSearch объединены в один процесс core шарда (D-23, раздел 7). Добавлен раздел 6.9 о резервном копировании (BKP-001--BKP-006): расписанием бэкапов rqlite и ZincSearch управляет scheduler, единый раздел UI показывает политику, историю и ход восстановления, бэкап ZincSearch делается только с реплики, минимальная топология ZincSearch --- мастер и реплика, восстановление узла ZincSearch автоматическое. Добавлены критерии приемки 27 и 28.

**Изменения v1.8.** Хранилище логов заменено: вместо форка ZincSearch с репликацией через NATS JetStream принят VictoriaLogs (D-07, ADR 0016 и 0017): сравнение кандидатов и проверка на 100 млн строк дали приём около 1 млн строк/с, диск 0,39× исходного текста, окно p95 около 10 мс. Репликации в самом VictoriaLogs нет, поэтому шард держит два независимых одиночных узла, которые питает vlagent (дисковый буфер на каждый узел), а gateway читает с узла без отставания и повторяет запрос на втором (DAT-008, DAT-010, DAT-011). Coordinator упразднен: выбор мастера и failover хранилища не нужны, остались модуль контура логов (здоровье узлов, снимки, восстановление) и vlagent (D-21, D-23). NATS JetStream больше не входит в базовую поставку шарда (D-03, 7.3). Требования ZF-1--ZF-8 к форку сняты: JWT в хранилище не нужен (единственный читатель --- gateway), окно идет по времени строки, retention по периоду и удалением по фильтру (DAT-006, DAT-008). Шлюз запуска RUN-015 теперь учитывает доступность узлов и очередь vlagent, а не мастера и `lag`. Восстановление узла (BKP-003, BKP-004) выполняется копированием снимка с живого узла с паузой записи порядка секунд или из проверенного бэкапа в S3. Q-10 снят, Q-13 и Q-16 переформулированы. Решения по транспорту между сервисами (NNG вместо HTTP/2, TLS и токен Pod для shim, TLS с логином и паролем для NATS) приняты владельцем позже и в этой версии в разделах 7 и 9 не отражены.

**Изменения v1.9.** Транспорт между сервисами отражен в разделах 7 и 9 (D-24, новая версия v1.8 не обновляла текст разделов): вместо HTTP/2 с mTLS для всех каналов без исключения выбран NNG 1.12.4 + mbedTLS 3.6.2 (`tls+tcp`, Protobuf-сообщения, ADR 0009 и 0010). Сервисы шарда и job-контроллер держат mTLS (сертификат выдается один раз при установке, как раньше); shim подключается по TLS с токеном задания (SEC-010, projected ServiceAccount token) вместо клиентского сертификата на каждый Pod, что снимает нагрузку на RUN-013 (Q-18). NATS, когда включен по триггерам T1--T3 (7.3), использует TLS с проверкой сервера и логином и паролем вместо mTLS. Обновлены 7.1 (строка транспорта), таблица компонентов 7, RUN-002, 9.2 и его таблица каналов, M0-спайк 2, риск экосистемы Nim (12) и условие пересмотра D-01.

**Изменения v1.10.** NATS убран из платформы полностью (D-03): решение v1.9 «NATS по триггерам T1--T3» снято владельцем, отдельного брокера для событий нет. События платформы (webhook, уведомления о доступной работе, fan-out статусов) идут только через outbox в rqlite; лестница при нехватке пропускной способности заканчивается уменьшением шарда (SHD-003), без добавления шины. Убраны раздел «Триггеры использования NATS» и строка «Шина» (7.1, 7.3), упоминания NATS в целях MVP (5), Event service (7), SEC-003 (11), D-24 (9.2) и M4 Enterprise scale (16). Официальный Helm-чарт NATS в `deploy/m0/helmfile.yaml` больше не нужен, если владелец не решит иначе при пересмотре D-03.

**Изменения v1.11.** Владелец подтвердил (2026-09-22), что NATS в платформу не возвращается (D-03 окончательно); для шины событий, если она когда-либо понадобится, рекомендация по ADR --- NATS, а не Dragonfly (durable JetStream против fire-and-forget Pub/Sub, нет multi-primary кластера у Dragonfly, лицензия BSL 1.1 вместо Apache-2.0). D-02 (rqlite) подтверждён отдельным сравнением с Percona XtraDB Cluster (ADR 0018): rqlite быстрее в 4--10х на захвате step и легче на порядок по памяти, PXC выигрывает только на пакетной вставке. Закрыты частью измерений `[M0-CHECK]`: RUN-013 (не выполняется, p95 до 7 с, ADR 0011), выбор клиента Kubernetes и кодека Protobuf (оба решены и используются, ADR 0011), пакетирование и VACUUM rqlite (ADR 0004), RPO логов при потере одного узла (ADR 0017), хеш-seed Lua (ADR 0003); RPO при потере обоих узлов VictoriaLogs, бэкап state rqlite и точный порог `gate_max_pending` остаются `[M0-CHECK]`. `docs/threat-model.md` переписан под VictoriaLogs/vlagent (без ZincSearch, NATS, coordinator), пункт про identity shim (Q-18) закрыт решением D-24; `.proto` (`logs.proto`) и `docs/state-machines.md` сверены с текущей архитектурой -- `.proto` требовал только правки одного комментария, Lua API и state machines изменений не потребовали.

**Изменения v1.12.** RUN-013 ослаблен владельцем (2026-09-22): цель при прогретых образах p95 ≤ 10 с вместо 3 с, по измерению ADR 0011 (p95 до 7,0 с на общем шумном стенде из двух рабочих узлов). Session mode (SES-001) не разрабатывается: условие (a) больше не выполняется, измеренный хвост укладывается в новую цель; пакетный запуск нескольких Pod (8,4--11,8 с на 50 Pod) и холодный образ shim (8 с) остаются отдельными, не пересмотренными целями. Q-14 закрыт этим решением.

**Изменения v1.13.** BKP-005 переписан (ADR 0019): бэкап и восстановление `state` --- встроенные `-auto-backup`/`-auto-restore` rqlite с S3-конфигом, своя команда `cicd admin restore-state` не нужна; измерено --- загрузка 6--17 мс, влияния на запись не выявлено, RPO на тестовом интервале точный. DAT-010 и NFR-007: RPO логов при потере обоих узлов VictoriaLogs измерен (ADR 0019, восстановление из S3-снимка через init-контейнер, данные восстановлены ровно на момент снимка). Осталось открытым: восстановление rqlite на многоузловом кластере (проверено на одном узле), регулярная процедура restore drill (сам факт восстановления проверен разово, не как повторяемая процедура).

**Устраненные несоответствия v1.0.** Число first-party расширений приведено к 10 в MVP и 20 к этапу 3 (D-13), критерий приемки 15 разделен на MVP-часть и часть этапа 3, нумерация вопросов раздела 21 начинается с Q-01. # 2 Анализ 20 CI/CD систем

## 2.1 TeamCity

Зрелый on-prem сервер, проекты и build configurations, сильные цепочки зависимостей, Kotlin DSL, build agents, удобная диагностика тестов.

| **Сильные стороны** | **Ограничения** | **Что переносим в аналог** |
|:---|:---|:---|
| Хорошая административная модель и UX; шаблоны конфигураций; параметры и артефактные зависимости. | Коммерческая модель; DSL тесно связан с API продукта; плагины JVM могут усложнять upgrade; control plane тяжелее компактных систем. | Взять иерархию проектов, templates, build chains, typed parameters и расследование тестов. |

## 2.2 Jenkins

Open-source automation server; Declarative/Scripted Jenkinsfile; controller/agents; огромная plugin ecosystem и shared libraries.

| **Сильные стороны** | **Ограничения** | **Что переносим в аналог** |
|:---|:---|:---|
| Максимальная расширяемость; почти любое окружение; durable/pausable pipelines; зрелая база интеграций. | Плагины работают внутри JVM и образуют dependency hell; Groovy/CPS сложен; безопасность и HA требуют дисциплины; UI и конфигурация неоднородны. | Взять императивный pipeline-скрипт с durable-исполнением (в нашей модели --- Lua с replay-журналом), простоту step API, shared libraries и extension points UI. Запретить in-process third-party плагины. |

## 2.3 GitHub Actions

Workflow в репозитории, events, jobs, reusable workflows, composite/Docker/JavaScript actions, hosted и self-hosted runners.

| **Сильные стороны** | **Ограничения** | **Что переносим в аналог** |
|:---|:---|:---|
| Лучший путь от commit/PR к workflow; большой marketplace; matrix; OIDC к облакам; понятная композиция. | Сильная привязка к GitHub; риск непинованных actions; YAML expressions имеют углы; локальная эмуляция неполна. | Взять event model, marketplace UX, reusable workflows и immutable pinning. |

## 2.4 GitLab CI/CD

Интегрированная модель stages/jobs/DAG, runners, includes/components, environments, deployments, variables и security reports.

| **Сильные стороны** | **Ограничения** | **Что переносим в аналог** |
|:---|:---|:---|
| Целостный SDLC; богатый YAML; child/parent pipelines; environment UX; self-managed вариант. | Большая платформа сложна в эксплуатации; часть функций зависит от tier; YAML rules/includes быстро усложняются. | Взять components с typed inputs, environments, review apps и reports, отделив CI от Git-хостинга. |

Multi-stage YAML, templates, variable groups, environments/checks, hosted/self-hosted agents, service connections.

## 2.6 CircleCI

Workflows, jobs, executors, orbs, caching/workspaces, hosted и self-hosted runners.

## 2.7 Travis CI

Простой `.travis.yml`, lifecycle phases, build matrix, conditions, caching и deployment providers.

| **Сильные стороны** | **Ограничения** | **Что переносим в аналог** |

SaaS control plane с self-hosted agents, queues/tags, dynamic pipelines, block/wait/trigger steps и plugins.

| **Сильные стороны** | **Ограничения** | **Что переносим в аналог** |
|:---|:---|:---|

# 6 Функциональные требования

## 6.1 Проекты и репозитории

**PRJ-001 Иерархия.** Организация содержит проекты; проект может наследовать policy, variables, профили исполнения (RUN-004) и libraries, но переопределение явно отображается.

**PRJ-002 SCM neutrality.** Один проект подключает несколько репозиториев GitHub, GitLab, Bitbucket или generic Git; SCM adapter не должен менять ядро scheduler.

**PRJ-003 Discovery.** Система автоматически обнаруживает pipeline-скрипт по настраиваемым путям (по умолчанию `.ci/pipeline.lua`), выполняет фазу метаданных (PIP-002) и создает preview триггеров, параметров и требуемых профилей исполнения до первого запуска.

**PRJ-004 Monorepo.** Path filters вычисляются по merge-base; поддерживаются include/exclude, ownership и запуск дочерних pipeline (`ci.run`) для изменившихся подпроектов. Функция `run.changed_paths()` доступна скрипту и записывается в журнал.

## 6.2 Pipeline-скрипты и исполнение

Pipeline --- это скрипт на Lua 5.4, исполняемый в песочнице pipeline-executor. Модель заимствует у Jenkins возможность писать обычный код (условия, циклы, обработка ошибок) и надежность durable-исполнения, но вместо CPS-трансформации Groovy использует журнал вызовов и воспроизведение (replay). Скрипт сам не выполняет работу: он описывает шаги, а каждый шаг исполняется отдельным контейнером в Kubernetes (6.4). Терминология: **job** --- именованный блок с общим образом, ресурсами и окружением; **step** --- один вызов `j.sh` или `j.use`, который выполняется отдельным Pod; **run** --- один запуск pipeline.

**PIP-001 Bundle и версионирование.** Каждый run хранит immutable bundle: исходный скрипт, commit SHA, digest всех подключенных Lua-модулей и плагинов, версию Lua API и версию рантайма. Изменение скрипта в репозитории не влияет на уже созданный run.

**PIP-002 Две фазы.** Скрипт возвращает таблицу `ci.pipeline{...}` с полями метаданных (`name`, `on`, `params`, `env`, `requires` --- профили исполнения, `storage`, `permissions`, `concurrency`, `timeout`) и функцией `main`. Фаза метаданных выполняется при discovery и при создании run в режиме без побочных эффектов: доступны только конструкторы типов и чистые функции. Фаза исполнения вызывает `main(run)`.

**PIP-003 Журнал вызовов.** `main` выполняется как сопрограмма. Каждый вызов host API, у которого есть побочный эффект или результат, записывается в append-only run journal: `(run_id, seq, тип, fingerprint вызова, результат)`. Сюда входят `ci.job`, `j.sh`, `j.use`, `j.env`, `ci.parallel`, `ci.spawn`, `ci.input`, `ci.run`, `ci.sleep`, `ci.now`, `ci.random`. Результат шага включает код выхода и `outputs` (STO-003), поэтому данные, переданные между шагами, воспроизводимы при replay. Вызовы должны быть приостанавливаемы сквозь `pcall`, чтобы обычная обработка ошибок Lua работала. Ожидание шага, approval или таймера освобождает executor и не занимает ресурсов кластера.

**PIP-004 Воспроизведение.** При падении, перезапуске или перебалансировке executor новый воркер выполняет тот же bundle с начала, подставляя результаты из журнала вместо реальных вызовов, пока не дойдет до первого вызова без записи; дальше исполнение идет штатно. Шаг, который был запущен, но не завершен на момент сбоя, не запускается повторно: job-контроллер по детерминированному имени Pod (RUN-002) сообщает его фактическое состояние. Если fingerprint вызова не совпал с записью журнала, run получает состояние `infrastructure_error` с кодом `script_nondeterminism`, а диагностика указывает `seq`, ожидаемый и фактический вызов.

**PIP-005 Детерминизм песочницы.** Обязательные меры: (a) удалены `io`, `os`, `debug`, `dofile`, `loadfile`, `package.loadlib`; `load` принимает только текстовые чанки; `collectgarbage` ограничен; (b) `math.random` заменен на журналируемый `ci.random`, время доступно только через `ci.now`; (c) `pairs` и `next` заменены итерацией в стабильном порядке (сначала последовательная часть, затем ключи, отсортированные по типу и значению); ключи-таблицы и ключи-функции запрещены, так как их порядок зависит от адресов; (d) хеш-seed строк Lua фиксируется при сборке (`luai_makeseed`, `src/executor/lua_glue.c`; ADR 0003, `tests/unit/tsandbox.nim`); (e) `tostring` и `%p` не выводят адреса; (f) глобальная среда защищается от записи после старта.

**PIP-006 Лимиты.** На каждый run действуют лимиты: память Lua-состояния (по умолчанию 64 MiB, реализуется через собственный аллокатор `lua_newstate`), CPU-бюджет между вызовами host API (счетчик инструкций через hook, по умолчанию 50 млн), число записей журнала (по умолчанию 100 000), ширина `parallel` и `matrix` (по умолчанию 1 000), суммарная длительность. Превышение завершает run состоянием `failed` с кодом лимита. Значения настраиваются политикой.

**PIP-007 Граф.** UI строит граф run по журналу; страница рендерится на сервере (UI-009), граф --- серверный SVG с обновлением фрагмента по SSE. Узлы: stage, job, step, parallel-ветки, spawn/wait и input. Порядок зависимостей задан кодом: `ci.spawn` возвращает handle, а `handle:wait()` возможен только для уже созданного handle, поэтому циклы структурно невозможны.

**PIP-008 Stages.** `ci.stage(name, fn)` группирует вызовы для UI, метрик и перезапуска с stage (PIP-015); stage не ограничивает параллелизм.

**PIP-009 Matrix.** `ci.matrix` строит декартово произведение осей с include/exclude, `max_parallel` и `fail_fast`; результат исполняется через `ci.parallel`. Лимит расширения проверяется при вызове и, где размер вычисляется статически, при preflight (PIP-016).

**PIP-010 Дочерние pipeline.** `ci.run(ref, params, opts)` создает дочерний run (в том же или другом проекте того же шарда, если разрешено политикой; кросс-шардовые вызовы не поддерживаются, SHD-002) и при `wait=true` приостанавливает родителя до результата. Дочерний run проходит policy как обычный, получает собственное storage (STO-001) и хранит ссылку на родителя.

**PIP-011 Библиотеки.** Lua-модуль публикуется в registry с SemVer, digest и декларацией входов и выходов. `require("lib/go@1.4.0")` разрешается через lockfile `.ci/lock.json` (имя, версия, digest); production policy может запретить mutable refs. Модуль загружается только по digest и исполняется в той же песочнице.

**PIP-012 Типизированные параметры.** Поле `params` использует конструкторы типов (`ci.string`, `ci.number`, `ci.bool`, `ci.choice`, `ci.list`, `ci.map`, `ci.secret`). Значения валидируются до старта run, а UI строит форму запуска из этих деклараций (13).

**PIP-013 Manual gates.** `ci.input{...}` приостанавливает run без занятия Pod и других ресурсов кластера. Approval содержит approver, timestamp, comment, policy snapshot и SHA; автор изменения не может одобрить собственный prod deploy при включенном separation-of-duties.

**PIP-014 Concurrency.** Поддержать concurrency group и политики queue, cancel-oldest, cancel-newest, задаваемые в `ci.pipeline{concurrency=...}`; lock lease восстанавливается после сбоя scheduler.

**PIP-015 Retries и перезапуск.** Retry шага или job создает новую attempt с тем же bundle и тем же storage run, если run еще активен. Retry завершенного run поддерживает режимы `full`, `failed-only` и `from-stage`: новый run воспроизводит журнал предыдущего до выбранной точки, подставляя успешные результаты, `outputs` и артефакты. Storage прежнего run не переиспользуется: восстанавливаются только зафиксированные артефакты и outputs, а содержимое workspace --- лишь при включенных снапшотах (STO-006) `[ОТКРЫТО Q-11]` `[M0-CHECK]`.

**PIP-016 Статическая проверка.** `cicd pipeline check` и серверный preflight выполняют фазу метаданных и статический анализ: запрещенные глобалы, неизвестные плагины и версии, несоответствие параметров схеме, вызовы host API вне `main`, известные превышения лимитов, неизвестные профили исполнения. Проверка не гарантирует завершаемость скрипта.

**PIP-017 IDE.** Поставляются типовые аннотации (`lua/stdlib/cicd.d.lua`, формат LuaLS) для автодополнения и проверки типов host API.

local go = require("lib/go@1.4.0")         -- модуль по lockfile (digest)

return ci.pipeline {
  name = "service-ci",
  on = {
    push = { branches = { "main" } },
    pull_request = {},
  },
  params = {
    deploy = ci.bool { default = false },
  },
  env = { IMAGE = "registry.example.com/team/service" },

      ci.job({ image = "golang:1.25-alpine" }, function(j)
        j.checkout()                       -- в /cicd/workspace/src
        go.test(j, { json = "test.json" })
        j.use("reports/go-test@1.2.0", { path = "test.json" })
      end)
    end)

    ci.stage("image", function()
      ci.job({ permissions = { registry = "write", oidc = "write" } }, function(j)
        local r = j.use("build/buildkit@2.1.0", {
          image = run.env.IMAGE .. ":" .. run.commit,
          provenance = true,
        })
        j.env { DIGEST = r.outputs.digest } -- передача данных следующим шагам
      end)
    end)

    if run.params.deploy and run.branch == "main" then

Пример показывает императивные возможности (обработка ошибок, ручное решение, параллельные ветки) и передачу данных между шагами через `.env`-файлы.

```lua
main = function(run)
  local ok = pcall(function()
    ci.job({ image = "registry.example.com/ci/tools:2" }, function(j)
      j.sh("./integration.sh")
    end)
  end)
  if not ok then
    ci.input {
      message = "Интеграционные тесты упали. Продолжить выкладку?",
      approvers = { "role:release-manager" },
      timeout = "4h",
    }
  end

  ci.job({ image = "alpine:3.21" }, function(j)
    -- шаг пишет пару KEY=VALUE в файл $CICD_OUTPUT и $CICD_ENV (STO-003)
    local r = j.sh([[echo "VERSION=1.$(date +%Y%m%d)" >> "$CICD_OUTPUT"
                     echo "VERSION=1.$(date +%Y%m%d)" >> "$CICD_ENV"]])
    ci.log("info", "версия: " .. r.outputs.VERSION)
    j.sh('echo "собираем $VERSION"')     -- VERSION уже в окружении шага
  end)

  local builds = ci.matrix {
    axes = { target = { "server", "worker" }, arch = { "amd64", "arm64" } },
    exclude = { { target = "worker", arch = "arm64" } },
    max_parallel = 3,
  }
  local jobs = {}
  for _, c in ipairs(builds) do
    jobs[c.target .. "-" .. c.arch] = function()
      ci.job({ image = "golang:1.25", profile = "build-" .. c.arch,
               workspace = "isolated" }, function(j)
        j.sh("make dist TARGET=" .. c.target)
      end)
    end
  end
  ci.parallel(jobs, { fail_fast = true })
end
```

## 6.4 Runs, очередь и исполнение

Платформа работает только внутри Kubernetes и не использует агентов: нет постоянных процессов-исполнителей на узлах, нет регистрации агентов и их heartbeat. Каждый step выполняется в собственном Pod (контейнере), который создает и наблюдает job-контроллер --- единственный компонент шарда, имеющий права в кластере (SEC-010).

**RUN-001 Run state.** Состояния run: created, compiling, queued, running, waiting, succeeded, failed, canceled, skipped, timed_out, infrastructure_error. Состояние `compiling` означает фазу метаданных и preflight. Переходы выполняются как compare-and-swap (`UPDATE ... WHERE id=? AND version=?`); все записи в rqlite сериализуются лидером кластера шарда. Состояния step: pending, starting, running, succeeded, failed, canceled, timed_out, lost.

**RUN-002 Диспетчеризация step.** Scheduler помещает step в очередь шарда, а job-контроллер получает ему задания по долгоживущему исходящему Protobuf-каналу NNG (REQ/REP, mTLS) (контроллер сам подключается к scheduler, входящих соединений в кластер нет). Для каждого step контроллер создает Pod с детерминированным именем `ci-<run>-<seq>-<attempt>`: повторное создание при ретрае канала возвращает `AlreadyExists` и безопасно (идемпотентность и fencing). Контроллер наблюдает Pod через Kubernetes watch (с возобновлением по `resourceVersion`) и передает scheduler только переходы состояния; heartbeat заданий нет. После перезапуска контроллер перечисляет Pod по меткам run и восстанавливает соответствие. Потеря самого контроллера обнаруживается по одному heartbeat на контроллер (в памяти scheduler, в rqlite не пишется), лидерство между репликами --- Kubernetes Lease. Шаг, Pod которого исчез без итогового статуса, получает состояние `lost` и повторяется только по retry policy.

**RUN-003 Fair scheduling.** Weighted fair queue между организациями и проектами; отдельные quotas для одновременных Pod, CPU/memory requests, объема storage и привилегированных возможностей.

**RUN-004 Профили исполнения.** Профиль (замена agent pools) задает: namespace, node selector и tolerations, RuntimeClass, ресурсы по умолчанию и максимумы, StorageClass, ServiceAccount без прав, класс NetworkPolicy, allowed projects, максимальный параллелизм, trust level. Job выбирает профиль полем `profile` или получает профиль по умолчанию из проекта. Только Linux-узлы; Windows и macOS не поддерживаются.

**RUN-005 Ephemeral.** Pod step создается в restricted Pod Security (non-root, без capabilities, seccomp RuntimeDefault, read-only root там, где образ позволяет). Успешные Pod удаляются сразу после снятия итогового статуса; неуспешные хранятся `debug_retention` (по умолчанию 1 ч) для диагностики. Осиротевшие Pod, PVC и Secret удаляются периодической сверкой по меткам `cicd.io/run` (GC).

**RUN-006 Cancellation.** Отмена доставляется контроллеру не более чем за 5 секунд p95; контроллер удаляет Pod с grace period (SIGTERM, затем SIGKILL); cleanup-шаг из `ci.finally` имеет отдельный timeout. Отмена run прерывает `main` исключением, которое можно перехватить только внутри блока `ci.finally`.

**RUN-007 Устойчивость потока логов.** Runner shim (RUN-010) передает лог в log collector (DAT-001) с sequence и checksum. При недоступности collector shim буферизует поток в файле на локальном томе Pod (по умолчанию до 64 MiB) и продолжает отправку по sequence после восстановления; при переполнении буфера пишущий процесс блокируется обратным давлением pipe, а не теряет данные. Память shim не зависит от объема лога. Длительная недоступность collector означает недоступность шарда (SHD-005), поэтому буфер рассчитан только на кратковременные сбои.

**RUN-008 Pipeline-executor.** Воркеры executor --- отдельные процессы (SEC-007), ведущие run на условиях lease с TTL, продлеваемым scheduler'ом в памяти (в rqlite пишется выдача lease и продление не чаще `lease_persist_interval`, по умолчанию 60 с; после рестарта scheduler действует grace TTL, а воркер подтверждает lease по `lease_token`). При потере executor другой воркер выполняет replay (PIP-004). Скрипт не имеет доступа к сети, БД и файловой системе; всё взаимодействие идет через Protobuf-канал к scheduler.

**RUN-009 Плотность.** Один воркер executor ведет много run (по одному Lua-состоянию на run) в пределах лимита памяти воркера и конфигурируемого числа run (по умолчанию 200) `[M0-CHECK]`.

**RUN-010 Runner shim.** Shim --- статический бинарный файл на Nim (≤ 5 MiB), не демон: он доставляется в Pod init-контейнером в общий `emptyDir` и служит entrypoint-обёрткой пользовательской команды (по образцу Tekton entrypoint). Shim: подготавливает окружение (загружает env-файл, STO-003), запускает команду как дочерний процесс, читает stdout/stderr и отправляет их collector'у, собирает `$CICD_ENV` и `$CICD_OUTPUT` после завершения, записывает итог в termination message (≤ 4 KiB: код выхода, причина, digest выходов) и завершает Pod с кодом команды. Образ пользователя не модифицируется и может быть любым Linux-образом. Shim использует токен задания (SEC-010) только для связи с collector и scheduler.

**RUN-011 Services.** Сервисные контейнеры (`services` в `ci.job`) запускаются отдельным Pod job'а с headless Service и DNS-именем внутри run; NetworkPolicy разрешает доступ только Pod того же run. Pod сервиса создается при первом обращении и удаляется при завершении job; он не входит в лог step'ов, но имеет собственный поток логов.

**RUN-012 Границы agentless-модели.** Привилегированные контейнеры и Docker-in-Docker не поддерживаются. Сборка образов выполняется плагином BuildKit через rootless buildkitd как сервисный Pod профиля. Задачи, которым необходим долгоживущий контейнер на весь job (например, интерактивная отладка или тяжелый прогрев кэша), используют session mode, зарезервированный на этап 3 (7.4) `[ОТКРЫТО Q-14]`.

**RUN-013 Задержка запуска.** Цель: от постановки step в очередь до старта пользовательского процесса p95 ≤ 10 с при прогретых образах (владелец ослабил порог 2026-09-22 по измерению ниже; было ≤ 3 с), p95 ≤ 8 с при холодном образе shim `[M0-CHECK]` (сценарий с холодным образом отдельно не измерялся). Измерено при старом пороге (ADR 0011, общий шумный стенд из двух рабочих узлов): p50 0,9--1,7 с, p95 до 7,0 с (создание Pod --- не узкое место, ~0,2 с; время у kubelet, хвост до 7 с) --- **в ослабленную цель укладывается**; пакет из 50 Pod --- 8,4--11,8 с, всё ещё выше цели, если запуск нескольких step пачкой станет обычным сценарием. Меры 1--3 раздела 7.4 (том, постоянные тома, предзагрузка образов) время kubelet не сокращают на этом стенде `[M0-CHECK]` на целевом кластере. Для сокращения задержки shim-образ предзагружается на узлы DaemonSet'ом (не исполняющим заданий); повторные запуски Pod над одним томом (RUN-014) и постоянные тома между run (STO-008) убирают из step повторную подготовку данных.

**RUN-014 Многократный запуск Pod над постоянным томом.** Pod step одноразовый, а состояние run хранится на постоянном томе (STO-001), поэтому Pod можно создавать заново и многократно: следующий step, retry step, повтор после потери узла или сбоя контроллера, повторный запуск того же образа для диагностики. Pod не хранит состояния между запусками: всё нужное берется с тома (`/cicd/workspace`) и из env-файлов (STO-003). Контроллер обязан: (a) создавать Pod любого step над уже существующим томом без повторной подготовки; (b) при retry сохранять содержимое тома, если policy не требует очистки (`clean`); (c) при `ReadWriteOnce` создавать Pod на узле, где том уже подключен, либо ждать его освобождения (STO-001); (d) не допускать более одного активного Pod на step (RUN-002). Идемпотентность самих шагов --- ответственность автора pipeline.

**RUN-015 Допуск запуска по состоянию контура логов.** Основной модуль всегда знает состояние контура логов (DAT-010) и подстраивает под него исполнение. Запуск step и сервисных Pod разрешен, только пока шлюз запуска открыт: хотя бы один узел VictoriaLogs находится в состоянии `up`, vlagent принимает записи, а очередь доставки vlagent для этого узла не превышает `gate_max_pending` (по умолчанию 256 MiB) `[M0-CHECK]`. Когда условие нарушено, шлюз закрывается: (a) scheduler не назначает step контроллерам, а контроллеры не создают новые Pod, даже для уже назначенных step; такие step остаются в очереди с причиной `logs_unavailable` (`steps.wait_reason`); (b) создание run, разбор скрипта, preflight, ожидание `ci.input` и отмена не блокируются (отмена удаляет Pod и не требует логов); (c) исполняющиеся step не прерываются платформой: их лог накапливается в буфере shim, а при его переполнении step блокируется обратным давлением (RUN-007); (d) UI показывает баннер «запуск задач приостановлен: контур логов недоступен», API отдает причину, а метрики и алерты фиксируют время закрытия (раздел 15). Шлюз закрывается не позднее чем через 10 с после потери последнего доступного узла или отказа приема vlagent и открывается, когда условие непрерывно выполняется `gate_stabilize` (по умолчанию 10 с); затем очередь возобновляется автоматически с учетом приоритетов и квот. После рестарта scheduler шлюз закрыт до получения первого состояния (fail-closed). Cleanup-шаги `ci.finally` подчиняются тому же правилу; аварийный обход запрета решает владелец `[ОТКРЫТО Q-16]`.

## 6.5 Логи, тесты, артефакты и cache

**DAT-001 Logs: источник истины --- VictoriaLogs.** Shim передает лог чанками (Protobuf, sequence и checksum) в log collector шарда. Collector (a) применяет redaction (DAT-002), (b) разбивает поток на строки с номером `ln` в пределах job, (c) пакетно отправляет строки в vlagent (`/insert/jsonline`, поля `_msg`, `_time`, `ln`, `job`, `run`; поток `_stream_fields=job`; тенант передается заголовками `AccountID`/`ProjectID`) и подтверждает sequence shim'у только после подтверждения приема vlagent; vlagent доставляет данные обоим узлам VictoriaLogs (DAT-008) и хранит очередь на диске отдельно для каждого узла. Ключ окна --- служебное время `_time` = базовое время job плюс `ln` миллисекунд (монотонно и уникально в пределах job; так измерено в ADR 0017), реальное время строки хранится в поле `ts` и показывается пользователю; поле `ln` хранится для якорей и сортировки по `(_time, ln)`. Собственного пути чтения у collector нет: весь просмотр идет через gateway (DAT-011). VictoriaLogs не дедуплицирует записи, поэтому collector отправляет каждую строку один раз, повтор после неопределенного ответа делается с тем же `ln`, а окно исключает дубли по `ln` `[M0-CHECK]`. Недоступность vlagent приводит к обратному давлению на shim (RUN-007). Копий лога в S3 в качестве источника истины нет: браузер, API и выгрузка читают только VictoriaLogs. ANSI разрешен после sanitization. Строки длиннее лимита (по умолчанию 64 KiB) разбиваются с пометкой продолжения.

**DAT-002 Redaction.** Известные значения secrets маскируются в collector до записи в VictoriaLogs и до любого пути, видимого браузеру; shim дополнительно выполняет best-effort маскирование значений, известных ему на момент старта step. Маскируются plain, URL-encoded и base64 forms в заданных пределах, включая значения, разорванные границей чанка (окно переноса ≥ длины самого длинного secret). Прямая запись шагов и плагинов в VictoriaLogs запрещена: сетевая политика (SEC-003) открывает vlagent только log collector'у, управляющий интерфейс узлов (снимки, удаление) --- только модулю контура логов, а чтение --- только шлюзу чтения.

**DAT-003 Artifacts.** Shim и плагины загружают артефакты напрямую в S3-совместимое хранилище по short-lived URL (multipart); SHA-256, size, media type, expiry, provenance и ACL сохраняются в rqlite. S3 --- хранилище артефактов и cache, но не логов.

**DAT-004 Cache.** Cache key immutable; restore-keys выбирают последний совместимый объект; защита от poisoning разделяет trusted/untrusted refs и проекты. Restore и save выполняются step'ом плагина в общее storage (STO-001) через S3. Cache не заменяет storage: он живет между run, storage --- внутри run. Для повторного использования каталогов между run без обмена через S3 предназначены постоянные тома (STO-008).

**DAT-005 Tests.** Нормализованная модель suite/case/attempt; duration history, flaky detection, owner, failure fingerprint и comparison с базовой веткой.

**DAT-006 Retention.** Раздельные политики для logs, artifacts, caches, audit, journal и provenance; legal hold запрещает GC выбранных runs. Retention логов задается общим сроком узлов VictoriaLogs (`-retentionPeriod`, разделы по дням отбрасываются целиком) и ограничением места (`-retention.maxDiskSpaceUsageBytes`); отдельные сроки для тенанта или типа данных выполняются удалением по фильтру (`/delete/run_task`, около 8 с на 1 млн строк) по расписанию модуля контура логов. Удаление тенанта --- удаление по его `AccountID`.

**DAT-007 Просмотр логов окном.** Пользователь никогда не загружает лог целиком: просмотрщик всегда работает с окном строк (по умолчанию 200 строк, не более 500 и не более 256 KiB на окно), которое сервер запрашивает у VictoriaLogs по диапазону времени строки внутри потока job (DAT-008, DAT-011); отставание отображаемого лога от вывода шага в пару секунд допустимо. Просмотрщик отдается как iframe с отдельного origin (`logs.<base-domain>`), атрибут `sandbox="allow-scripts"` без `allow-same-origin`, CSP `frame-ancestors` ограничен origin UI. Доступ дается токеном (IAM-004) со сроком не более 60 с, привязанным к job или run. Окно рендерится на сервере готовым HTML (одна строка --- один элемент с якорем `L<ln>`); клиентский код (≤ 20 KiB) только подгружает соседнее окно при прокрутке и держит в DOM не более трех окон, отбрасывая дальние, поэтому JS heap просмотрщика не превышает 5 MiB при логе любого размера (UI-008). Поддерживаются переход по номеру строки, по времени и к найденному совпадению поиска, live tail (SSE, новые строки добавляются в конец последнего окна, старые окна отбрасываются), ANSI после sanitization и deep-link на строку или диапазон (`#L1234`, `#L100-L140`; при открытии по ссылке загружается окно вокруг строки). Размер и позиция сообщаются родителю через `postMessage` с проверкой origin. Без JS та же информация доступна страницей `/jobs/{id}/log?from=N` со ссылками «предыдущее окно» и «следующее окно».

**DAT-008 VictoriaLogs и его требования.** LogStore --- внутренний интерфейс с операциями `append`, `window`, `tail`, `search`, `export`, `delete` (по фильтру и тенанту), `snapshot`; единственная продуктовая реализация --- VictoriaLogs (Go, единый бинарник, Apache-2.0, upstream без форка); интерфейс нужен для тестовой подмены и возможной замены продукта. Состав контура логов шарда: два независимых одиночных узла VictoriaLogs на постоянных томах (StatefulSet, по одному Pod), агент vlagent с дисковым буфером и отдельной очередью на каждый узел (`-remoteWrite.url` дважды, `-remoteWrite.maxDiskUsagePerURL`) и gateway чтения. Сведения о продукте получены из документации и флагов бинарника v1.52.0 и подтверждены замерами M0 (ADR 0017). Свойства, на которые опирается платформа: (a) хранилище не реплицирует данные между узлами, отказоустойчивость дает доставка в оба узла; при недоступном узле vlagent копит очередь и после возврата узла доставляет ее (измерено: 2 млн строк за 7--19 с, без потерь и дублей); (b) мультитенантность через заголовки `AccountID` и `ProjectID`; (c) флаги узла: `-storageDataPath`, `-retentionPeriod`, `-retention.maxDiskSpaceUsageBytes`, `-delete.enable`, `-memory.allowedBytes` или `-memory.allowedPercent`, `-tls`, `-httpAuth.*`; (d) снимки разделов `POST /internal/partition/snapshot/create|list|delete` (создаются за десятки миллисекунд, восстановление копированием каталога раздела); (e) поиск по полям и тексту без отдельной настройки индекса; (f) отсеивание дублей в самом хранилище нет. Клиентские сертификаты (mTLS) у VictoriaLogs есть только в enterprise-редакции, поэтому внутри шарда канал защищен TLS с проверкой сервера и логином и паролем. Замена требований к форку ZincSearch (ZF-1--ZF-8): ZF-1 (JWT в хранилище) не нужен, пользовательский доступ проверяет gateway, он же единственный читатель; ZF-2 retention: срок узла, отбрасывание разделов по дням и удаление по фильтру (DAT-006); ZF-3 live tail: `/select/logsql/tail` с `offset=0s` (задержка p50 1,5 с) или опрос запросом; ZF-4 ограничения: `limit` и `timeout` запроса, `-memory.allowedBytes`, лимит памяти Pod `[M0-CHECK]`; ZF-5 закрытый сетевой контур (наружу публикуется только gateway); ZF-7 оконный запрос: выборка N строк потока job по диапазону `_time` в порядке возрастания (6,8 мс p50 на 100 млн строк независимо от смещения); ZF-8 export: потоковый ответ запроса блоками по времени с постоянной памятью gateway `[M0-CHECK]`. Цели M0 (подтверждены на 100 млн строк, ADR 0017): окно p95 ≤ 100 мс (получено 9,7 мс), дисковое усиление ≤ 3× (0,39×), приём ≥ 5 MiB/s на job (около 100 MiB/s суммарно), перезапуск узла с 100 млн строк (первый запрос через 0,5 с).

**DAT-009 Скачивание.** Кнопка «скачать» --- единственный сценарий, читающий лог целиком. Gateway отдает его потоком (`Content-Disposition`, опциональный gzip), потоком блоками по времени из VictoriaLogs (DAT-008) буфером не более 4 MiB и не удерживая лог в памяти; поток учитывает redaction и квоту скачиваний. Для завершенных run ссылка подписывается на короткое время.

**DAT-010 Долговечность логов и модуль контура логов.** Источник истины --- два независимых узла VictoriaLogs шарда на постоянных томах (DAT-008); единственный узел не поддерживается. Модуль контура логов --- часть процесса core шарда, в котором вместе работают scheduler и log collector (D-23): (a) опрашивает узлы (`/health`, `poll_interval`, по умолчанию 2 с) и метрики vlagent (объем очереди на узел) и считает узел `down` после `fail_threshold` (по умолчанию 3) неудачных опросов подряд, а узел с непустой очередью --- `catching_up`; (b) сообщает gateway состояние узлов (ClusterState): читать можно с узла `up` с минимальной очередью, а при ошибке запрос повторяется на втором; (c) выполняет снимки, их выгрузку и проверку, автоматическое восстановление узлов и удаление по retention (BKP-001--BKP-006); (d) передает scheduler'у внутри процесса готовность контура для шлюза RUN-015. Выбора мастера, повышения и failover хранилища нет. Состояние (узлы, бэкапы, политики) и лидерство хранятся в rqlite шарда: таблицы `log_nodes`, `backups`, `backup_policies` и lease `shard-core` с fencing token (общий с scheduler); запись выполняется только при изменениях, результаты опросов в rqlite не пишутся. Активен один экземпляр core, второй (standby) --- рекомендация. Топология по умолчанию `[ОТКРЫТО Q-13]`: два узла VictoriaLogs и vlagent; в малой установке они могут работать на одном кластере без отдельных узлов Kubernetes, но на разных постоянных томах. Очередь vlagent лежит на своем томе и является единственным местом, где хранятся еще не доставленные строки; ее размер ограничен (`maxDiskUsagePerURL`), при переполнении шлюз запуска закрывается раньше (RUN-015, `gate_max_pending`). Цель RPO логов: около нуля при потере одного узла --- **измерено** (ADR 0017: очередь vlagent догоняет 2 млн строк за 7--19 с без потерь и дублей после возврата узла); не более интервала бэкапа (по умолчанию 1 ч) при потере обоих узлов --- **измерено** (ADR 0019: снимок в S3 через контейнер-компаньон, узел уничтожен, восстановление в новый под из S3 --- ровно данные на момент снимка, ни строки лишней или потерянной сверх интервала). Контур логов входит в ядро шарда (SHD-005). Копия завершенных логов в S3 как gzip-архив (`logs.archive`, по умолчанию выключена) допускается только для долгого хранения и compliance и не читается UI.

**DAT-011 Чтение логов.** Все чтения логов (окно, поиск, live tail, export) идут к одному узлу VictoriaLogs, который выбирает gateway по состоянию из ClusterState (DAT-010): узел `up` с пустой или минимальной очередью vlagent; при ошибке или таймауте запрос повторяется на втором узле (проверено: при остановке узла ни один запрос не терялся). Отставание отображаемого лога от вывода шага на пару секунд допустимо, поэтому нет отдельных механизмов свежести: нет чтения из памяти collector'а. Gateway кэширует выбор на несколько секунд; когда доступных узлов нет, он возвращает временную ошибку с `Retry-After`, а просмотрщик повторяет запрос автоматически. Читающая нагрузка приходится на один узел, поэтому запросы ограничены по размеру и времени (DAT-008), а превышение NFR-005 пересматривается решением D-20. Готовый прокси vmauth с политикой `first_available` допустим вместо кода выбора узла в gateway (проверен в M0).

## 6.6 Environments и deployment

**DEP-001 Environment.** Environment имеет tier, URL, protection rules, concurrency, credentials binding, deployment history и optional Kubernetes target.

**DEP-002 Checks.** Перед job выполняются approvals, change window, branch/tag rule, external policy webhook и exclusive lock.

**DEP-003 Deployment record.** Запись содержит artifact digest, source SHA, environment, actor, pipeline, timestamps, status и rollback reference.

**DEP-004 Promotion.** Один immutable artifact продвигается между средами; rebuild при promotion по умолчанию запрещен.

**DEP-005 Rollback.** Rollback --- новый audited deployment существующего digest/config snapshot, а не переписывание истории.

## 6.7 Host API pipeline-скриптов (Lua API v1)

Нормативны имена, семантика и правила журналирования. Точные сигнатуры фиксируются в ADR по итогам этапа 0 и после этого не меняются в пределах версии API v1. Модуль подключается как `local ci = require("cicd")`.

| **Функция** | **Где вызывается** | **Журнал** | **Назначение** |
|:---|:---|:---|:---|
| `ci.pipeline{...}` | Верхний уровень скрипта | Нет | Метаданные и `main`; возвращается из скрипта |
| `ci.string`, `ci.number`, `ci.bool`, `ci.choice`, `ci.list`, `ci.map`, `ci.secret` | Фаза метаданных | Нет | Типизированные параметры (PIP-012) |
| `ci.stage(name, fn)` | `main` | Да | Группа для UI, метрик и перезапуска |
| `ci.job(opts, fn)` | `main` | Да | Job: `image`, `profile`, `resources`, `timeout`, `retry`, `services`, `permissions`, `env`, `secrets`, `workspace` (`shared` по умолчанию или `isolated`); `fn` получает `j` |
| `j.checkout(opts)` | Внутри `job` | Да | Step: получение исходников через SCM-плагин в `/cicd/workspace/src` |
| `j.sh(cmd, opts)` | Внутри `job` | Да | Step: команда shell в Pod с образом job (или `opts.image`); результат: `code`, `outputs`, необязательно stdout |
| `j.use(ref, inputs)` | Внутри `job` | Да | Step плагина по закрепленной ссылке; входы проверяются по JSON Schema плагина; результат: `code`, `outputs` |
| `j.env(tbl)` | Внутри `job` | Да | Переменные окружения для следующих шагов job (без запуска Pod) |
| `j.artifact`, `j.cache` | Внутри `job` | Да | Загрузка, скачивание, save/restore |
| `ci.parallel(tbl, opts)` | `main` | Да | Параллельные ветки, `fail_fast` |
| `ci.spawn(fn)`, `h:wait()`, `h:cancel()` | `main` | Да | Асинхронные ветки; DAG задается порядком spawn/wait |
| `ci.matrix{...}` | `main` | Нет | Комбинации осей с include/exclude и лимитом |
| `ci.input{...}` | `main` | Да | Ручное решение без занятия ресурсов кластера (PIP-013) |
| `ci.deploy(env, fn)` | `main` | Да | Job в защищенном environment с проверками DEP-002 |
| `ci.run(ref, params, opts)` | `main` | Да | Дочерний run (PIP-010) |
| `ci.sleep(seconds)`, `ci.now()`, `ci.random()` | `main` | Да | Таймер без Pod, время, случайное число |
| `ci.finally(fn)` | `main` | Да | Очистка при отмене и ошибке |
| `ci.log(level, msg)`, `ci.fail(msg)` | Везде | Да | Сообщение в лог run; явный отказ |

Непосредственно перед step job-контроллер создает эфемерный Kubernetes Secret с разрешенными значениями, монтирует его в Pod step и удаляет вместе с Pod; значения маскируются collector'ом (DAT-002).

## 6.8 Storage и обмен данными между шагами

**STO-001 Storage run.** Для run создается один том (PersistentVolumeClaim), который job-контроллер создает при первом step, монтирует по пути `/cicd/workspace` в Pod каждого step и удаляет по завершении (STO-006). Размер задается `ci.pipeline{storage={size=...}}` в пределах квоты проекта, StorageClass --- профилем исполнения. Предпочтителен режим `ReadWriteMany` (параллельные jobs на разных узлах); при `ReadWriteOnce` контроллер закрепляет все Pod run за одним узлом через pod affinity, что ограничивает параллелизм ресурсами узла `[ОТКРЫТО Q-11]`. Pod step одноразовый, а том постоянен на время run, поэтому Pod можно создавать заново и многократно (RUN-014). Storage доступно только Pod того же run; между run том по умолчанию не переиспользуется (исключение --- постоянные тома, STO-008).

**STO-002 Раскладка.** `/cicd/workspace` --- общий каталог всех step; `j.checkout()` кладет исходники в `/cicd/workspace/src`; переменная `CICD_WORKSPACE` указывает на корень. Для job с `workspace="isolated"` контроллер монтирует подкаталог тома `.jobs/<job-id>` (`subPath`) как `/cicd/workspace`, чтобы параллельные ветки не мешали друг другу. Вне тома доступны: `/cicd/tmp` (`emptyDir` на step) и `/cicd/run` (служебные файлы shim: `CICD_ENV`, `CICD_OUTPUT` и каталог `plugin/` файлового контракта плагинов, PLG-008).

**STO-003 Передача данных через .env.** Каждому step доступны два файла в формате dotenv-подмножества: `$CICD_ENV` --- переменные, которые получат все последующие step того же job (и попадут в журнал как `j.env`), и `$CICD_OUTPUT` --- значения, которые вернутся скрипту в `r.outputs` (журналируются, воспроизводимы при replay). Формат: строки `NAME=VALUE`; значение в кавычках допускает escape-последовательности; многострочное значение --- `NAME<<DELIM` ... `DELIM`. Файл разбирает shim парсером (не `source` оболочкой). Ограничения: имя `[A-Z_][A-Z0-9_]*`, значение ≤ 8 KiB, ≤ 256 ключей и ≤ 64 KiB на step. Между jobs данные передает Lua-код (значения `outputs` в опциях следующего `ci.job`) либо файлы в общем workspace.

**STO-004 Безопасность обмена.** Deny-list имен (SEC-011): `LD_*`, `PATH`, `IFS`, `BASH_ENV`, `ENV`, `SHELL`, `HOME`, `CICD_*`, `NODE_OPTIONS`, `PYTHONPATH` и им подобные; значение, содержащее известный secret, отклоняется с ошибкой `secret_in_output`. Outputs и env не предназначены для секретов и хранятся в rqlite; секреты передаются только handle (6.7).

**STO-005 Storage и артефакты.** Storage живет до конца run и не является долговременным хранилищем. Результаты, которые нужны после run, сохраняются как артефакты (DAT-003); зависимости между run --- cache (DAT-004).

**STO-006 Жизненный цикл.** Том удаляется через `storage_retention` после завершения run (по умолчанию 0 для succeeded, 24 ч для failed и timed_out для диагностики). Для перезапуска с stage (PIP-015) допускаются снапшоты тома на границах stage (VolumeSnapshot, опция профиля, по умолчанию выключена) `[ОТКРЫТО Q-11]`. Осиротевшие тома удаляются сверкой по меткам (RUN-005). Шифрование в покое обеспечивает StorageClass.

**STO-007 Ошибки и квоты.** При исчерпании тома step получает ошибку записи, run --- код `storage_exhausted`; объем и число томов ограничены квотой проекта (RUN-003); использование отображается в UI и метриках.

**STO-008 Постоянные тома между run** (этап M2). Pipeline может запросить именованный том, который сохраняется после run и повторно используется следующими: `ci.pipeline{storage={persist={name="build", scope="branch"}}}`. Цель --- убрать из запуска повторные checkout, загрузку зависимостей и сборку с нуля (`j.checkout()` выполняет fetch вместо clone). Правила: (a) том выдается run эксклюзивно по lease, одновременно одному run; остальные ждут либо получают чистый том по политике; (b) ключ тома --- проект, имя, область `scope` (`project`, `branch` или `pipeline`) и уровень доверия ref; том никогда не разделяется между trusted и untrusted refs (по аналогии с DAT-004), форки получают только чистые тома; (c) содержимое считается недоверенным: политика может требовать очистки (`clean`) до старта; (d) размер и число томов ограничены квотой, вытеснение по LRU и TTL (по умолчанию 14 дней без использования); (e) том привязан к профилю исполнения и его StorageClass. Реализуется поверх PVC, снапшоты не требуются `[ОТКРЫТО Q-11]`.

## 6.9 Резервное копирование шарда

**BKP-001 Планирование в scheduler.** Резервное копирование --- системная задача процесса core шарда: расписанием управляет scheduler, выполнением --- модуль контура логов того же процесса. Бэкапы не являются run pipeline, не создают Pod step и не подчиняются шлюзу запуска RUN-015. Цели: `state` (rqlite шарда) и `logs` (VictoriaLogs). Политика каждой цели: `enabled`, `interval` (для `state` по умолчанию 5 мин, что следует из RPO в NFR-007; для `logs` 1 ч), `retention` (3 последних годных бэкапа плюс новейший проверенный), `verify_interval` (по умолчанию 24 ч). Одновременно выполняется не более одного бэкапа на цель; владение обеспечивает lease `shard-core`.

**BKP-002 Единый раздел UI и API.** Раздел «Резервные копии» (роль Platform admin) общий для `state` и `logs`: политика (расписание, retention, проверка), ручной запуск «сделать бэкап сейчас», история и статусы (`running`, `uploaded`, `verified`, `bad`, `failed`), размер, размер и число снимков (для `logs`), время, результат проверки, состояние узлов VictoriaLogs и очередей vlagent, ход автоматического восстановления и журнал потерь при нем. Те же действия доступны через REST (`GET` и `POST /api/v1/shards/{id}/backups`, `PUT /api/v1/shards/{id}/backup-policy`) и CLI (`cicd admin backup`). Ручные запуски, изменения политики и автоматические решения (восстановление узла, закрытие шлюза) пишутся в audit (SEC-005); изменение политики требует подтверждения.

**BKP-003 Снимок логов и выгрузка.** Снимок разделов делается на узле `up` без отставания доставки (очередь vlagent пуста) вызовом `POST /internal/partition/snapshot/create`; он занимает десятки миллисекунд и не останавливает ни узел, ни прием, ни запуск задач. Снимок выгружается в S3 инструментом в Pod узла (контейнер-компаньон над тем же томом, например rclone) с подсчетом SHA-256 и манифестом (разделы, размер, число записей, время); архив сохраняется, только если контрольная сумма совпала, после чего снимок на узле удаляется. Если подходящего узла нет, бэкап откладывается и повторяется, а при отсутствии успешного бэкапа дольше двух интервалов создается алерт. Снимок раздела измерен на 0,02 с (ADR 0017), поэтому пауза заведомо короче, чем потребовалось бы для закрытия шлюза запуска; сама логика «бэкап не закрывает RUN-015» в коде modуля контура логов не реализована и не проверена `[M0-CHECK]`.

**BKP-004 Автоматическое восстановление узла VictoriaLogs.** Восстановление узла всегда автоматическое. Узел с потерянным диском или поврежденными данными модуль контура логов восстанавливает так (проверено в M0): (1) кратко приостанавливает доставку vlagent (запись задерживается, шлюз запуска RUN-015 закрывается на время порядка секунд), (2) создает снимок на втором узле `up`, (3) копирует его в том восстанавливаемого узла (143 МиБ за 0,13 с; для 100 млн строк около 3,5 ГиБ), (4) очищает очередь vlagent для этого узла, чтобы строки, попавшие и в снимок, и в очередь, не задвоились, (5) запускает узел и возобновляет доставку. Если второго узла нет, узел восстанавливается из новейшего бэкапа со статусом `verified` (бэкап `bad` не используется никогда), а доставка возобновляется из очереди vlagent; записи между бэкапом и началом очереди теряются, диапазон потерь пишется в audit и показывается в UI. Если потеряны оба узла, сначала восстанавливается первый узел из бэкапа, затем второй копированием с первого; шлюз запуска закрыт, пока нет ни одного узла (RUN-015). Способ выполнения копирования (init-контейнер или Job над томом) и выгрузка в S3 фиксируются в ADR M0 `[M0-CHECK]`.

**BKP-005 Бэкап и восстановление rqlite.** Бэкап и восстановление `state` --- встроенные флаги rqlite `-auto-backup`/`-auto-restore` с JSON-конфигом (`type: s3`, интервал, ключи, `bucket`, `path`); свой инструмент или команда `cicd admin restore-state` не нужны (правило «не писать свое», ADR 0019). Бэкап делает только лидер и только при изменении данных; **измерено** (ADR 0019): загрузка 6--17 мс, RPO на тестовом интервале точный (потеряны ровно записи после последнего бэкапа, ни одной лишней), влияния на запись не выявлено. Восстановление происходит на старте узла, до входа в кластер; раздел UI показывает список и статусы бэкапов. Восстановление `-auto-restore` проверено на одном узле; поведение на многоузловом кластере (по документации rqlite данные реально применяет только узел, ставший лидером, остальные получают их через Raft) не проверено `[M0-CHECK]`.

**BKP-006 Проверка и алерты.** Раз в `verify_interval` проверяется новейший бэкап: для `logs` --- восстановление снимка во временный экземпляр VictoriaLogs и сравнение числа записей и контрольной выборки со значениями манифеста, для `state` --- восстановление во временный экземпляр rqlite и проверка целостности `[M0-CHECK]`. Алерты: нет успешного бэкапа дольше двух интервалов, нет проверенного бэкапа дольше двух периодов проверки, нет узла для снимка без отставания, идет восстановление, при восстановлении потеряны записи (раздел 15).

# 7 Архитектура

Платформа --- набор микросервисов, каждый из которых является отдельным процессом со своим Deployment или StatefulSet и независимым масштабированием; общий код живет в `src/common`. Слияние сервисов в один процесс не предусмотрено. Установка одного узла (одна реплика каждого сервиса, один шард) --- это конфигурация Helm, а не другая архитектура. Работа вне Kubernetes не поддерживается. Компоненты делятся на два уровня: глобальные (обслуживают все шарды, не хранят данные тенантов) и компоненты шарда (7.3).

| **Компонент** | **Уровень** | **Ответственность** | **Состояние/протокол** |
|:---|:---|:---|:---|
| Web UI и API service | Глобальный | Серверный рендеринг HTML, формы, фрагменты (HTMX), SSE, постоянные URL, extension points, REST v1, auth; маршрутизация запроса в шард по directory | Stateless; HTTPS; без прямого доступа к БД шарда |
| Directory | Глобальный | Каталог: тенант → шард, шарды и их состояние, идентичности пользователей и членство | Собственный малый rqlite (3 узла); кэш в API на 60 с |
| Plugin registry | Глобальный | Manifest, signature, OCI digest, compatibility, trust | OCI registry + каталог в rqlite directory |
| Core шарда (один процесс) | Шард | Модули: scheduler (очередь step, квоты, приоритеты, lease executor'ов и job-контроллеров, допуск запуска по RUN-015, расписание бэкапов); log collector (прием логов от shim, redaction, отправка в vlagent); модуль контура логов (опрос узлов VictoriaLogs и очередей vlagent, снимки и их выгрузка, автоматическое восстановление узлов, retention удалением, BKP-001--BKP-006) | rqlite шарда authoritative; Protobuf-каналы NNG с mTLS; vlagent; API узлов VictoriaLogs; таймеры lease в памяти |

Модули core шарда работают в одном процессе (D-23), поэтому scheduler знает состояние контура логов без сетевых вызовов; в тексте модули называются своими именами (scheduler, log collector, модуль контура логов). Приём логов и планирование конкурируют за ресурсы одного процесса, поэтому у каждого модуля свои потоки и лимиты памяти, а при необходимости прием логов выносится в отдельный процесс без изменения контрактов. Pipeline-executor исполняет пользовательский код и обязан работать в отдельных процессах с ограничениями (SEC-007) даже при установке из одного узла. Общение между сервисами --- Protobuf поверх NNG (`tls+tcp`) с mTLS (таблица внутренних каналов в разделе 9); shim подключается по TLS с токеном задания вместо клиентского сертификата (D-24, Q-18); сервисы шарда не обращаются к БД других сервисов.

## 7.2 Надежность и консистентность

- rqlite шарда --- источник истины для state machine тенантов шарда. Каждый переход состояния --- CAS-запись (`UPDATE ... WHERE version=?`). Записи, определяющие состояние, журнал и аудит, идут только через строгую запись rqlite; queued writes (асинхронные, с небольшим риском потери при падении узла) допускаются лишь для данных, которые можно восстановить (метрики, вспомогательные отметки времени).

- В SQLite и rqlite нет `SELECT FOR UPDATE SKIP LOCKED` и advisory locks. Постановка step на исполнение делает одна атомарная запись с подзапросом (пример ниже); конкуренция между экземплярами scheduler исключается тем, что очередь профиля принадлежит одному активному экземпляру по lease-строке с fencing token; при отказе владельца очередь перехватывается после TTL.

- Потеря уведомления о доступной работе не теряет step: scheduler периодически (`reconcile_interval`) пересматривает строки `queued`, а job-контроллер после переподключения сверяет свои Pod со списком активных step шарда.

- Outbox pattern обязателен для событий, порожденных транзакцией. Consumers используют idempotency key и inbox table либо естественный unique constraint.

- Запись journal выполняется той же транзакцией, что и изменение состояния, вызвавшее возобновление скрипта: executor накапливает записи за один интервал исполнения и фиксирует их одним пакетом.

- Webhook deduplication key: provider + delivery ID; при отсутствии ID --- HMAC(normalized payload + time bucket).

- Все long-running операции представлены operation resource и не удерживают HTTP connection, кроме SSE и потока выгрузки лога.

- Уровни чтения rqlite: `strong` или linearizable для постановки в очередь и переходов состояния; `weak`/`none` с параметром свежести для списков UI `[M0-CHECK]`.

- Состояние Pod в Kubernetes --- единственный источник истины о фактическом исполнении step; rqlite хранит намерение и итог. Расхождения устраняет сверка контроллера (RUN-002): Pod без записи удаляется, запись без Pod получает состояние `lost`.

```sql
UPDATE steps
   SET state = 'dispatched', controller_id = :controller, pod_name = :pod,
       version = version + 1
 WHERE id = (SELECT id FROM steps
              WHERE state = 'queued' AND profile_id = :profile
              ORDER BY priority DESC, queued_at
              LIMIT 1)
   AND state = 'queued'
RETURNING id, job_id, run_id, ordinal, attempt;
```

Пример выше --- эскиз; поддержка `RETURNING` и атомарность через Raft-лог проверяются в M0 `[M0-CHECK]`.

## 7.3 Шардирование и эксплуатация rqlite

Владелец выбрал масштабирование шардированием. Шард (cell) --- самостоятельный набор сервисов и хранилищ: собственный rqlite, core (scheduler, log collector и модуль контура логов в одном процессе), executor, event service, log gateway, контур логов (два узла VictoriaLogs и vlagent) и один или несколько job-контроллеров в целевых кластерах. Тенант (организация со всеми проектами, runs и логами) целиком принадлежит одному шарду `[ОТКРЫТО Q-12]`.

**SHD-001 Directory.** Directory хранит соответствие тенант → шард, состояние шардов и идентичности пользователей с членством в организациях. API и события маршрутизируются в шард по directory; результат кэшируется на 60 с и сбрасывается при переносе тенанта. Запрос, попавший в неверный шард, получает Problem Details с кодом `wrong_shard` и повторяется клиентом.

**SHD-002 Изоляция отказов.** Отказ или деградация шарда затрагивает только его тенанты. Между шардами нет распределенных транзакций, общих очередей и общих данных, кроме directory и S3; поэтому кросс-шардовый `ci.run` в MVP не поддерживается (PIP-010).

**SHD-003 Размещение и рост.** Новый тенант получает шард по политике размещения (наименьшая загрузка по весу или явное указание). Емкость шарда определяется M0-бенчмарком по NFR-006 с запасом 2×; при достижении 70 % емкости создается новый шард, а очередные тенанты направляются в него. Перенос существующего тенанта в MVP --- офлайн-операция административного инструмента: остановка приема, выгрузка строк тенанта из rqlite, перенос логов тенанта через export (DAT-008, тенант выбирается заголовком `AccountID`) и повторный прием в целевом шарде, переключение записи directory; онлайн-перенос вынесен за MVP `[ОТКРЫТО Q-12]`.

**SHD-004 Шард-ориентированность с первого среза.** Каждая таблица шарда содержит `tenant_id`; все идентификаторы содержат префикс шарда либо разрешаются через directory; конфигурация и метрики помечены `shard`. В MVP развертывается один шард, но код не должен предполагать единственность.

**SHD-005 Контур логов --- часть ядра шарда.** Core шарда (scheduler, log collector, модуль контура логов), vlagent, log gateway и узлы VictoriaLogs входят в ядро шарда. Пока ни один узел VictoriaLogs не доступен или vlagent не принимает записи, запуск новых step запрещен, а очередь ждет (RUN-015); при недоступности core шард недоступен целиком (новых логов нет, смотреть их некому, интерфейс шарда недоступен). Режима работы без логов нет, требований к независимой доступности приема и просмотра логов не предъявляется; отказоустойчивость обеспечивают два узла, очереди vlagent и бэкапы (DAT-010).

**Ограничения rqlite, учитываемые проектом.** Записи проходят через лидера и Raft; одиночные записи обходятся по документации от 10 до сотен запросов в секунду, а пакетирование (bulk API, транзакции) повышает пропускную способность примерно на два порядка; при создании снапшота и при VACUUM записи блокируются. Следствия: heartbeat, логи и предложения очереди в rqlite не пишутся (RUN-002, DAT-001); запись группируется пакетами; снапшоты и VACUUM настраиваются и планируются вне пиков. Измерено (ADR 0004): пакет из 500 строк --- около 4 000 строк/с против 10--60 одиночных записей/с (разница ~100х), простой при VACUUM на ~20 МБ --- 1,1--2,6 с.

**Лестница при нехватке записи в rqlite шарда.** (1) Сократить и укрупнить записи: пакеты, вынос эфемерных данных из БД. (2) Уменьшить шард: вынести часть тенантов в новый шард (SHD-003). Замена rqlite на другую СУБД не предусмотрена; интерфейс `StateStore` с набором conformance-тестов остается внутренней границей ядра для тестовых подмен.

**События платформы --- только outbox в rqlite.** Webhook-события, доставка уведомлений о доступной работе и fan-out статусов идут через outbox-таблицу (consumers с idempotency key и inbox table, 7.2); отдельной шины нет, состояние остается в rqlite. Если доставка систематически не укладывается в NFR-003 даже после уменьшения шарда (SHD-003) и укрупнения записей, это возврат к D-03: владелец решает, какой брокер добавить.

**Резервное копирование.** Каждый шард резервируется независимо: бэкапы rqlite и логов планирует и выполняет core шарда, управление --- из единого раздела UI (BKP-001--BKP-006). Бэкап и восстановление логов измерены (ADR 0017: снимок 0,02 с, восстановление узла 8,5 с); бэкап и восстановление `state` (rqlite) через API и S3 не проверены `[M0-CHECK]`.

## 7.4 Ускорение запуска step: многократный запуск Pod и session mode

Обычные контейнеры нельзя добавить в уже созданный Pod, а ephemeral containers предназначены для отладки и не подходят для рабочей нагрузки `[проверить]`, поэтому базовая модель --- один Pod на step (RUN-002). Ее цена --- задержка запуска RUN-013 на каждый step. Чтобы снизить ее, модель строится на многократном запуске одноразовых Pod над постоянным томом, а полноценный session mode остается резервом `[ОТКРЫТО Q-14]`. Меры применяются по порядку.

1. **Многократный запуск Pod над томом (RUN-014, MVP).** Pod не хранит состояния, поэтому создается заново для каждого step и retry, а всё состояние run --- на томе (STO-001) и в env-файлах (STO-003). Step не тратит время на подготовку данных.

2. **Постоянные тома между run (STO-008, этап M2).** Checkout, зависимости и промежуточные результаты переживают run; step стартует с прогретого каталога.

3. **Предзагрузка образов** shim и типовых образов профиля на узлы (RUN-013, цель ослаблена до p95 ≤ 10 с).

4. **Session mode (резерв, этап 3).** Применяется, только если п. 1--3 не дают достижения RUN-013.

**SES-001 Условие включения.** Режим session mode разрабатывается, если выполняется одно из условий: (a) замеры M0 показывают, что p95 запуска step по RUN-013 не достижим на целевых кластерах даже при мерах 1--3 --- **не выполнено**: измеренный p95 7,0 с укладывается в ослабленную цель 10 с (ADR 0011, решение владельца 2026-09-22), условие (a) снято; остаётся открытым при пакетном запуске (50 Pod --- 8,4--11,8 с) и на менее мощных кластерах; (b) значимая доля job состоит из десятков коротких step с одним образом.

**SES-002 Суть.** Для job с включенным режимом создается один Pod с одним образом; shim работает как его entrypoint в режиме сессии: устанавливает исходящий поток к scheduler по токену задания (SEC-010), получает команды следующих step и исполняет каждую как дочерний процесс в том же контейнере. Постоянного процесса на узле нет; сессия живет не дольше job. Step с другим образом исполняется отдельным Pod.

**SES-003 Требования сохраняются.** Журнал, outputs, storage (STO-001), redaction, restricted Pod Security и отмена работают так же, как в базовой модели; отмена step в сессии --- сигнал процессу и его группе. Разделение секретов между step обеспечивается очисткой окружения дочернего процесса; при недоверенных pipeline режим не включается (SEC-007).

**SES-004 Интерфейс не меняется.** Скрипт pipeline и Lua API v1 одинаковы в обоих режимах; режим выбирается профилем исполнения (RUN-004).

## 10.2 Протокол плагинов

**PLG-008 Protobuf-протокол.** Контракт плагина описан в `.proto` (пакет `cicd.plugin.v1`). Step-плагин --- обычный контейнер в Pod step (RUN-010) с файловым контрактом на общем storage: shim записывает запрос `ExecuteStep` в файл `$CICD_PLUGIN_REQUEST` (сообщение с префиксом длины: varint + Protobuf, в каталоге `/cicd/run/plugin/`), плагин читает его, выполняет работу в `/cicd/workspace`, пишет `StepResult` в `$CICD_PLUGIN_RESULT` и завершается; логом служат stdout и stderr, которые собирает shim. Такой контракт не требует от плагина ни сети до платформы, ни постоянного соединения, ни SDK на конкретном языке. Service-плагины (trigger, secret provider, notifier, policy check, report parser) работают как отдельные сервисы по HTTP/2 или unix socket и в первом сообщении `Hello` согласуют версию протокола (N и N-1). Максимальный размер сообщения по умолчанию 4 MiB, неизвестные поля игнорируются, удаленные номера полей резервируются. Совместимость проверяется в CI инструментом проверки breaking changes для `.proto`, а conformance-контейнер запускается до публикации плагина. Эскиз схемы:

```proto
syntax = "proto3";
package cicd.plugin.v1;
import "google/protobuf/struct.proto";

message Hello        { uint32 protocol = 1; string plugin = 2; string version = 3; }
message ExecuteStep  {
  uint32 protocol = 5;                        // версия контракта (N или N-1)
  string step_id = 1;
  google.protobuf.Struct inputs = 2;          // проверены по JSON Schema плагина
  map<string, string> secret_handles = 3;     // имена, не значения
  string workspace = 4;                       // /cicd/workspace
}
message StepResult   { string step_id = 1; int32 exit_code = 2; google.protobuf.Struct outputs = 3; }
```

Входы шага проходят путь Lua-таблица -> канонический JSON -> проверка по JSON Schema плагина -> `google.protobuf.Struct`. Скрипты и конфигурация остаются человекочитаемыми, а на проводе используется Protobuf.

**PLG-001 Isolation.** Third-party плагин никогда не загружается в процесс control plane. Step работает в отдельном Pod step без доступа к control plane, кроме токена задания; service extensions --- в отдельном process/pod по versioned protocol.

**PLG-002 Capabilities.** Манифест объявляет network, workspace, artifacts, cache, secrets, oidc, privileged, host mounts и `ui.contribute`. Capabilities `privileged` и `host mounts` в MVP не удовлетворяются (RUN-012, SEC-004). Policy может запретить остальные или потребовать approval.

**PLG-003 Supply chain.** Marketplace принимает только immutable OCI digest, SBOM, provenance и signature. UI показывает publisher, permissions, vulnerabilities и last audit.

**PLG-004 Compatibility.** Protocol использует semantic versioning; server поддерживает N и N-1; conformance suite запускается до публикации.

**PLG-005 Configuration.** Каждый plugin поставляет JSON Schema с defaults, secrets annotations и UI hints; неизвестные fields отклоняются в strict mode.

**PLG-006 Updates.** Обновление не изменяет существующие runs; pipeline pin фиксирует digest. Автообновление разрешено только для выбранного SemVer range и после policy scan.

**PLG-007 UI contributions.** Плагин с capability `ui.contribute` вносит панели в extension points UI (UI-002). Панель отдается как iframe с отдельного origin (`x.<base-domain>/<plugin>/`), атрибут `sandbox="allow-scripts allow-forms"` без `allow-same-origin`, CSP `frame-ancestors` ограничен origin UI. Контекст (проект, run, job, пользователь, права) передается подписанным токеном (IAM-004), а не cookie. Плагин не имеет доступа к DOM основного UI; обмен размером и навигацией идет через `postMessage` с проверкой origin. Администратор одобряет UI-вклад отдельно и может отозвать его без удаления плагина.

# 11 Безопасность

## 11.1 Модель угроз

| **Угроза** | **Основной контроль** |
|:---|:---|
| Недоверенный PR извлекает production secret | Trust level refs; protected environments; fork jobs without secrets; explicit approval |
| Poisoned cache/artifact | Namespace by trust boundary; digest verification; immutable keys; provenance |
| Malicious plugin | Signature, capabilities, sandbox, network deny, no in-process code |
| Побег из Lua-песочницы pipeline-скрипта | Белый список окружения, отдельный непривилегированный процесс, seccomp, без сети и БД, ограничения CPU/памяти, fuzzing host API |
| Подмена или порча журнала run | Hash-chain записей журнала, проверка при replay, append-only, запись только из executor |
| Обход авторизации при просмотре логов и панелей | Токены на 60 с, отдельный origin, sandbox-iframe, VictoriaLogs только во внутреннем контуре, gateway --- единственный читатель, запросы ограничены тенантом (`AccountID`) и потоком job, redaction до записи |
| Ошибки безопасности памяти на границе Nim и C | Санитайзерные сборки, fuzzing парсеров, лимиты входных данных, обертки с `=destroy`, минимум `cast` и небезопасного кода |
| Компрометация Pod step или токена задания | Токен привязан к Pod и attempt и живет минуты (SEC-010), restricted Pod Security, default-deny NetworkPolicy, ephemeral Pod, нет доступа к БД и Kubernetes API |
| Компрометация job-контроллера | Минимальный Role в namespace профиля, без cluster-wide прав и `pods/exec`, исходящее соединение, mTLS identity, аудит действий (SEC-010) |
| Инъекция через env-файл (`LD_PRELOAD`, `PATH`) | Парсер dotenv-подмножества в shim, deny-list имен, лимиты (SEC-011, STO-004) |
| Побег из контейнера или соседство тенантов на узле | Namespace и квоты на тенанта, RuntimeClass с песочницей (gVisor или Kata) для недоверенных pipeline, отдельные профили и узлы (SEC-012) |
| Secret leaks in logs | Redaction в collector до записи в VictoriaLogs (DAT-002) и best-effort в shim, ephemeral Secrets, structured secret handles, disable shell tracing, retention controls |
| Webhook spoof/replay | Provider signature, timestamp window, delivery dedupe, IP policy optional |
| Dependency confusion | Pinned components, private registry priority, digest allowlist, SBOM |
| Unauthorized deployment | Environment RBAC, separation of duties, immutable approval snapshot, audit |

**SEC-001 Encryption.** TLS 1.3 preferred/TLS 1.2 minimum; envelope encryption AES-256-GCM; master keys from KMS or Vault transit; rotation without mass plaintext exposure.

**SEC-002 OIDC federation.** Jobs запрашивают signed token с audience, subject organization/project/pipeline/environment/ref, TTL \<= 10 minutes и unique jti.

**SEC-003 Network.** Pod step и сервисные Pod получают default-deny NetworkPolicy (ingress закрыт; egress --- DNS, log collector и scheduler шарда, остальное по allow rules, выведенным из plugin capabilities и project policy). VictoriaLogs (узлы), vlagent и rqlite доступны только сервисам шарда, а Pod step достигают их лишь через collector.

**SEC-004 Privileged.** Privileged container, Docker socket, hostNetwork, hostPID и hostPath не поддерживаются в MVP (RUN-012); Pod Security restricted на namespace профиля блокирует их независимо от платформы.

**SEC-005 Audit.** Audit append-only, hash-chained по partition и экспортируется в WORM/SIEM; чтение/изменение credentials также журналируется без значений.

**SEC-006 Compliance.** Предусмотреть controls mapping к SOC 2/ISO 27001, data retention, DPA, tenant export/delete; сертификация не является MVP feature.

**SEC-007 Изоляция pipeline-executor.** Воркер --- отдельный непривилегированный процесс или контейнер: seccomp-профиль, файловая система только для чтения (кроме ограниченного tmpfs), нет сети и доступа к БД, rlimit на CPU и память, один Lua-state на run, уничтожаемый по завершении; общих таблиц и глобальных состояний между run нет.

**SEC-008 Целостность журнала.** Каждая запись журнала содержит хеш предыдущей; при replay цепочка проверяется, нарушение переводит run в `infrastructure_error` с кодом `journal_corrupted`.

**SEC-009 Граница C.** Внешние C-библиотеки (Lua, TLS, кодеки) используются в закрепленных версиях, собираются в CI с санитайзерами, а парсеры недоверенных данных (XML отчетов, Protobuf от плагинов, HTTP/2 фреймы) имеют лимиты входа и fuzz-тесты.

**SEC-010 Токен задания и права контроллера.** Pod step получает только projected ServiceAccount token (audience `cicd-shard`, TTL 10 минут, привязка к Pod), смонтированный в служебный каталог shim; `automountServiceAccountToken` у ServiceAccount step выключен, прав в Kubernetes API у него нет. Collector и scheduler проверяют подпись токена по опубликованным ключам кластера и сопоставляют имя Pod с ожидаемым attempt step (fencing) `[M0-CHECK]`. Job-контроллер использует Role только в namespace профиля (pods, persistentvolumeclaims, secrets, services, leases, events), без `pods/exec` и cluster-wide прав; bootstrap-токен обменивается на mTLS identity (IAM-003), все его действия аудируются.

**SEC-011 Env-файл.** Файлы `CICD_ENV` и `CICD_OUTPUT` разбираются парсером dotenv-подмножества, а не оболочкой; имена проверяются по deny-list (STO-004), размеры ограничены, значения со структурой управляющих последовательностей отклоняются; нарушение завершает step с кодом `env_rejected`.

**SEC-012 Изоляция тенантов в кластере.** Pod разных тенантов не делят namespace `[рекомендация]`: namespace на тенанта или профиль с ResourceQuota, LimitRange и NetworkPolicy; для недоверенных pipeline (форки) профиль использует RuntimeClass с песочницей ядра (gVisor или Kata) и отдельные узлы.

# 13 UI и пользовательские сценарии

UI строится как MPA, а не SPA: HTML целиком формируется на сервере, клиентский код --- только прогрессивное улучшение. Обоснование --- профиль использования: в CI/CD смотрят редко и кратко, поэтому постоянные затраты памяти клиента (состояние, виртуальный DOM, клиентский маршрутизатор, большие бандлы) не оправданы, а затраты сервера на рендеринг по запросу малы и масштабируются вместе со stateless API service. Постоянные URL и корректная работа Back/Forward следуют из этого выбора. HTMX применяется для фильтров, действий и панелей; SSE --- для статуса и логов. WebSocket допускается только если двунаправленность действительно нужна. Каждое действие доступно через REST и CLI.

**UI-001 Постоянные ссылки.** Каждая сущность (organization, project, pipeline, run, stage, job, step, artifact, test case, environment, deployment, execution profile, shard, plugin, audit event) имеет стабильный URL; значимые подэлементы --- якоря (`#step-3`, `#L120`, `#test-<fingerprint>`). Состояние фильтров, сортировки, страницы и раскрытых панелей кодируется в URL. У каждого элемента есть действие «копировать ссылку». Ссылка открывается у другого пользователя с тем же результатом в пределах его прав.

**UI-002 Extension points.** UI предоставляет реестр точек расширения по образцу Jenkins: `dashboard.widget`, `project.tab`, `run.tab`, `job.tab`, `environment.panel`, `list.column`, `parameter.control`, `nav.item`, `page.banner`. Вклад бывает декларативным (настройка администратора без кода: колонка списка из полей run, баннер, сохраненное представление) либо панелью плагина в iframe (PLG-007). В MVP реализуются `run.tab`, `dashboard.widget` и `parameter.control`; остальные точки --- этап 3.

**UI-003 Представления.** Пользователь и администратор сохраняют представления списков (фильтры, колонки, группировка); представление адресуется URL и может быть общим для проекта или организации.

**UI-004 Динамические списки.** Списки runs, jobs, tests и профилей исполнения обновляются на месте: SSE для статусов только на видимой вкладке и только пока сущность активна (соединение закрывается по терминальному состоянию и при скрытии вкладки), поллинг с backoff как запасной вариант; пагинация курсором на сервере; обновление не сбрасывает раскрытые элементы, выделение и позицию прокрутки.

**UI-005 Динамические элементы.** Форма запуска строится по типам параметров (PIP-012) с зависимыми полями и валидацией; retry, cancel и approve выполняются без перезагрузки страницы, а без JS работают как обычные POST-формы.

**UI-006 Графики.** Графики (длительность, очередь, доля успешных, flaky, использование профилей исполнения и storage) рисуются на сервере в SVG без JS; улучшение (наведение, масштаб) --- небольшим скриптом, размещаемым на том же сервере. У каждого графика есть таблица-альтернатива и постоянная ссылка на состояние (диапазон, фильтры).

**UI-007 Граф run.** DAG и временная шкала с критическим путем строятся по журналу (PIP-007) в SVG, с таблицей-альтернативой для доступности.

**UI-008 Бюджет клиентской памяти.** Экономия памяти на клиенте --- приоритет наравне с сервером. Каждая страница укладывается в бюджет NFR-016: JS ≤ 50 KiB gzip (включая HTMX), JS heap после загрузки ≤ 10 MiB, узлов DOM ≤ 3 000, HTML ответа ≤ 300 KiB; страница просмотра логов (iframe) --- heap ≤ 5 MiB и узлов DOM ≤ 1 500 при логе любого размера. Правила: (a) нет клиентского состояния, кроме URL и полей формы; нет фреймворков и клиентских маршрутизаторов; (b) все списки и таблицы разбиваются на страницы на сервере (по умолчанию 50 записей), «бесконечной» прокрутки с накоплением DOM нет; (c) графики --- серверный SVG, не более 500 точек на график; граф run --- не более 300 узлов SVG, остальное группируется по stage и раскрывается отдельным запросом; (d) логи --- только окнами (DAT-007), не более трех окон в DOM, окно не более 500 строк и 256 KiB; (e) SSE-подписки закрываются на скрытой вкладке и при терминальном состоянии, не более одной подписки на страницу; (f) iframe плагинов создаются лениво при раскрытии вкладки и уничтожаются при закрытии, а их вклад в heap ограничен тем же бюджетом. Автотест e2e открывает эталонные страницы (run с 1 000 job, лог на 100 млн строк, список из 10 000 runs) в Chromium, измеряет heap через CDP и размер DOM и падает при превышении бюджета.

**UI-009 Серверный рендеринг.** Сервис UI не хранит состояние сессии в памяти и рендерит страницы потоково (chunked-ответ, без сборки всего HTML в памяти): расход памяти на запрос ограничен (по умолчанию 8 MiB) и не зависит от размера данных. Страницы завершенных run и job неизменяемы: они кэшируются по ETag, а фрагменты для HTMX отдаются теми же шаблонами, что и полные страницы. Каждый экран обязан работать без JS, за исключением live-обновлений и iframe-просмотра логов (NFR-009).

| **Экран** | **Обязательное содержимое** |
|:---|:---|
| Dashboard | Pinned projects, failing default branches, running/queued, deployments, состояние шардов и профилей исполнения; виджеты extension point |
| Project | Pipelines, recent runs, repository status, environments, schedules, settings; сохраненные представления |
| Pipeline | Скрипт с подсветкой, результат `check`, параметры, триггеры, версии библиотек, журнал вызовов последнего run |

# 14 CLI и локальная разработка

- CLI `cicd` (единый статический бинарник на Nim) поддерживает login, project, pipeline check/run, run watch/cancel/retry, logs (окно и скачивание), artifacts, profiles, shards и admin diagnostics.

- `cicd pipeline check` выполняет фазу метаданных и статический анализ скрипта (PIP-016) локально во встроенном Lua, разрешает библиотеки через lockfile и не требует сервера; вывод пригоден для IDE problem matcher.

- `cicd run --local` --- инструмент разработчика `[рекомендация]`: исполняет тот же скрипт локально, запуская каждый step контейнером Docker или Podman с тем же shim-контрактом и локальным каталогом вместо storage; явно сообщает, какие server features не эмулируются (approvals, OIDC federation, environments, NetworkPolicy). Это не поддерживаемая среда исполнения платформы (4.2).

- Все команды имеют `--help`, machine-readable `--output json`, стабильные exit codes и не печатают tokens/secrets.

- SDK: клиентская библиотека на Nim (из OpenAPI и `.proto`); для авторов плагинов --- `.proto`-контракты, шаблон плагина и стандартная кодогенерация для Go, Python, TypeScript и Rust; типовые аннотации Lua для IDE (PIP-017); conformance test container для протокола плагинов.

|:---|:---|

| Tracing | Webhook -\> preflight -\> queue -\> Pod -\> steps -\> reports; W3C trace context передается в Pod через окружение shim без sensitive baggage |
| Logs | Structured JSON, request/run/job/step/shard IDs, sampling для success, полный error; PII/secrets filtering |
| Health | /live only process; /ready checks critical dependencies; detailed admin diagnostics protected |
| Alerts | Oldest queue age, no schedulers, потеря связи с job-контроллером, Pod в Pending дольше порога, сбои создания PVC, осиротевшие ресурсы, задержка записи rqlite и частые смены лидера, рост очереди vlagent, закрытый шлюз запуска (нет доступного узла) дольше порога, заполнение тома узла VictoriaLogs или очереди vlagent, нет успешного или проверенного бэкапа в срок и нет узла для снимка (BKP-006), идущее восстановление узла и потери записей при нем, ошибки replay (`script_nondeterminism`, `journal_corrupted`), тренд роста RSS, error budget burn, storage saturation, backup failure |

- Состояния контура логов (узлы, очереди vlagent, бэкапы) платформа получает сама: модуль контура логов (core шарда) опрашивает узлы и vlagent (DAT-010) и показывает их в разделе «Резервные копии», на административных страницах и в собственных метриках.

- Резервное копирование каждого шарда (rqlite и логов) планирует scheduler core, выполняет его модуль контура логов, а управляют им из единого раздела UI (BKP-001--BKP-006); дополнительно копируются object-storage versioning/lifecycle, encryption keys и configuration export; directory резервируется отдельно; очередь vlagent хранит только еще не доставленные строки и не является источником истины. Логи не имеют другого источника, поэтому RPO логов задан в NFR-007 `[ОТКРЫТО Q-13]`.

- Upgrade выполняется preflight check, затем backward-compatible миграциями схемы, rolling services и postflight. Down migration для destructive schema не обещается; rollback бинарника поддерживается в окне совместимости.

- Образ shim версионируется вместе с control plane, а job-контроллер создает Pod только с образом shim, совместимым с версией протоколов N или N-1; сервер предупреждает и затем отклоняет протоколы вне support window. Обновление контроллера --- rolling с Kubernetes Lease, без потери наблюдаемых Pod (RUN-002).

# 16 Миграция из существующих систем

Импортеры генерируют Lua-скрипты (не YAML): результат --- portable draft из скрипта, lockfile и отчета потерь.

| **Источник** | **Импортируется автоматически** | **Требует ручной проверки** |
|:---|:---|:---|
| Jenkins | Declarative stages, agents/labels (в профили исполнения), environment, sh/bat, parallel, junit, artifacts | Scripted Groovy, arbitrary plugins, CPS semantics, credentials bindings |
| TeamCity | Projects, build configurations, templates, parameters, VCS roots, artifact/snapshot dependencies | Kotlin custom code, server plugins, agent requirements (сопоставление с профилями исполнения), edge cases |
| GitHub Actions | Triggers, jobs/needs, matrix, env, container, run, common actions mapping | JavaScript actions, permissions differences, expressions, services networking |
| GitLab CI | Stages/jobs, needs, rules subset, artifacts/cache, environments, includes | Complex rules, child pipelines, GitLab-specific reports and services |
| CircleCI | Jobs/workflows, executors, matrix, cache/workspace | Orbs without mapping, dynamic config |
| Travis CI | Languages/images, phases, matrix, cache, conditions subset | Deployment providers and addon-specific behavior |

Импортеры Drone, Bitbucket Pipelines, Semaphore и Bamboo вынесены в backlog после этапа 5; для Bamboo это соответствует сроку окончания жизни Bamboo Data Center (2.13).

**MIG-001 Dry run.** Importer не создает production resources сразу: формирует portable draft (Lua-скрипт и lockfile), mapping report и список unsupported constructs с severity.

**MIG-002 Differential validation.** Для выбранных pipelines параллельно запускаются старая и новая системы; сравниваются exit status, artifacts digests, tests и deployment intent.

**MIG-003 Cutover.** Webhook ownership переключается после green observation period; rollback сохраняет старую конфигурацию и запрещает двойной deploy через environment lock.

# 17 План реализации

Реализацию ведет Claude, поэтому вместо плана для команды и календарных сроков задана последовательность вертикальных срезов с проверяемыми критериями выхода. Объем измеряется срезами, а не месяцами; владелец принимает решения в конце каждого этапа. Оценка предполагает переиспользование rqlite, S3, OIDC provider, OCI registry, BuildKit, Kubernetes и Lua; собственные замены увеличивают объем.

# 18 Тестирование

- Unit: Lua host API, типы параметров, state transitions, RBAC, redaction (включая разрыв секрета границей чанка), scheduling and fairness, hash-chain журнала, парсер dotenv-подмножества и deny-list имен.

- Determinism и replay: property-based тесты убивают executor в каждой точке журнала и проверяют, что после replay граф и результаты идентичны прогону без сбоев; отдельные тесты `script_nondeterminism`.

- Contract: OpenAPI backward compatibility, Protobuf-протокол N/N-1, plugin conformance, SCM webhook fixtures, общие тестовые векторы Protobuf с Go и Python.

- Integration (на kind или k3d): rqlite/S3/Vault/Kubernetes/VictoriaLogs и vlagent, network loss, duplicate events, expired leases, переподключение job-контроллера и сверка Pod, повторное создание Pod с тем же именем, смена лидера rqlite во время постановки step, блокировка записи при snapshot, RWX и RWO storage, маршрутизация между двумя шардами и `wrong_shard`.

- End-to-end: push/PR/manual/schedule, matrices, artifacts, cache trust boundaries, approval, deploy and rollback, permalinks для каждой сущности.

- Security: SAST/SCA/container/IaC scans, secret-leak corpus (включая путь через iframe), SSRF, webhook replay, корпус побегов из Lua-песочницы, fuzzing host API и парсеров, plugin sandbox escape review, penetration test.

- Resilience: pod kills (включая job-контроллер и Pod step), drain узла, отказ провижининга PVC, DB failover, object storage throttling, перезапуск и отказ узла VictoriaLogs (чтение переключается на второй, очередь vlagent догоняется без потерь и дублей), остановка обоих узлов (проверка закрытия и открытия шлюза запуска), переполнение очереди vlagent, потеря тома узла VictoriaLogs (автоматическое восстановление копированием снимка или из бэкапа), недоступность collector во время step, clock skew, partial region failure, остановка одного шарда.

- Performance: постановка step и задержка запуска Pod (RUN-013), webhook burst, нагрузка одного шарда и 10 шардов, 5 MiB/s логов на job, оконные запросы на 100 млн строк, потоковая выгрузка большого лога, replay журнала 10 000 записей, million-run listing with cursor pagination.

- Soak и память: 72-часовой прогон, рост RSS, LeakSanitizer на интеграционном наборе (включая shim и job-контроллер), проверка лимитов памяти executor и collector.

- Клиентская память: e2e-набор в Chromium измеряет JS heap, DOM и размер ответа эталонных страниц и сравнивает с бюджетом UI-008; тест выполняется без JS для основных сценариев.

- Upgrade: every supported previous version to current with real-sized anonymized DB; rollback within compatibility window.

# 19 Критерии приемки MVP

1. Из push и pull/merge request GitHub/GitLab создается ровно один run; повторный webhook не дублирует его.

2. Скрипт с 1000 вызовов `ci.job` и matrix проходит preflight менее чем за 2 секунды p95 (NFR-014); ошибки типов параметров и статически вычислимые превышения matrix дают понятную ошибку до очереди, а динамические превышения лимитов (PIP-006) завершают run контролируемо с кодом лимита.

3. При 500 одновременных step и свободных ресурсах кластера queue latency соответствует NFR-003; ни один step не исполняется двумя Pod одновременно после гонки, повтора канала или переподключения контроллера (детерминированное имя Pod, fencing).

4. Отключение scheduler/API pod и убийство pipeline-executor в любой точке не теряют queued/running state: replay восстанавливает позицию скрипта без повторного исполнения завершенных вызовов и без ручной правки БД.

5. Secret из Vault доступен только разрешенному step, не присутствует в API, audit, artifacts, журнале run, Lua-состоянии, VictoriaLogs или проверочном log corpus; эфемерный Secret удален вместе с Pod.

6. Fork PR не получает protected variables, OIDC production claims и trusted cache namespace.

7. Cancellation, retry и timeout соответствуют state machine и не оставляют Pod, PVC и Secret после cleanup SLA.

8. JUnit отображает suites/cases/failures/durations, сравнение с default branch и flaky history.

9. Artifact upload/download проверяет SHA-256; истекшая ссылка не работает; ACL проекта применяется.

10. Production environment требует заданных approvers и branch policy; deployment фиксирует неизменяемый artifact digest.

11. Профили исполнения на двух разных Kubernetes-кластерах (например, kind и управляемый кластер) проходят одинаковый normative conformance suite, в том числе при storage RWX и RWO.

12. OpenAPI/CLI покрывают все основные действия UI; browser automation подтверждает Firefox/Chrome, keyboard navigation и работу основных сценариев без JS (кроме live updates и iframe-просмотра логов).

13. Резервная копия rqlite восстанавливается в чистый кластер в пределах RPO/RTO; audit chain verification успешна; узел VictoriaLogs с потерянным диском восстанавливается автоматически (копия снимка со второго узла или проверенный бэкап логов) и догоняет очередь vlagent в пределах RPO логов (NFR-007).

14. Helm install/upgrade проходит на двух поддерживаемых Kubernetes minor versions; documented rollback работает.

15. 10 MVP-расширений (4.1) имеют schema, signed immutable release, permissions manifest, документацию и integration tests; остальные 10 расширений --- критерий выхода этапа 3.

16. Soak 72 ч (NFR-013) пройден для сервисов шарда, executor, job-контроллера, log collector и shim; LeakSanitizer не сообщает об утечках.

17. Запрос к просмотрщику логов без токена или с просроченным токеном получает отказ; VictoriaLogs недоступен снаружи; в хранилище логов и очереди vlagent нет незамаскированных секретов из проверочного корпуса.

18. Корпус побегов и попыток недетерминизма (доступ к `io`/`os`, `pairs` по ключам-таблицам, чтение адресов, бесконечный цикл, выделение памяти сверх лимита) отклоняется или завершается контролируемой ошибкой.

19. Для каждой сущности и якоря из UI-001 открытие ссылки в новом сеансе дает тот же экран (автотест).

20. Два последовательных step одного job и step параллельной ветки видят общий `/cicd/workspace`; значение из `$CICD_OUTPUT` доступно скрипту как `r.outputs` и воспроизводится при replay; имена из deny-list, превышение лимитов и секрет в значении отклоняются с кодами `env_rejected` и `secret_in_output` (STO-003, STO-004, SEC-011).

21. Лог на 100 млн строк открывается окном на заданной строке и на найденном совпадении (окно ≤ 500 строк, p95 ≤ 300 ms; измерено ≈ 10 ms); полный лог отдается только по кнопке «скачать» потоком с буфером gateway ≤ 4 MiB независимо от размера; при недоступности collector во время step строки не теряются (RUN-007); отказ одного узла VictoriaLogs не влияет ни на прием, ни на просмотр логов (чтение переключается на второй узел, DAT-010, DAT-011, NFR-015); недоступность core шарда (scheduler, log collector, модуль контура логов) означает недоступность шарда, деградированного режима нет (SHD-005).

22. Два шарда работают независимо: запрос в неверный шард получает `wrong_shard` и перенаправляется по directory; остановка одного шарда не влияет на run другого (SHD-001, SHD-002).

23. Эталонные страницы (run с 1 000 job, лог на 100 млн строк, список из 10 000 runs) укладываются в бюджет клиентской памяти UI-008 и NFR-016 (JS heap ≤ 10 MiB, для просмотра логов ≤ 5 MiB; автотест), а основные сценарии работают без JS.

24. Pod step, убитый в любой момент (kill Pod, retry, потеря узла), пересоздается над тем же томом и продолжает работу без потери данных предыдущих step; не более одного активного Pod на step (RUN-014, RUN-002).

25. Постоянный том между run (этап M2): второй run той же ветки не повторяет checkout и использует содержимое тома; run из недоверенного ref (форк) получает только чистый том, а том trusted-ветки ему недоступен; одновременно том используется одним run (STO-008).

26. При недоступности обоих узлов VictoriaLogs или vlagent новые Pod не создаются, run и step остаются в очереди с причиной `logs_unavailable`, интерфейс показывает причину; шлюз закрывается не позднее 10 с; исполняющиеся step не прерываются, их лог доходит после восстановления без потерь в пределах буфера shim; после возврата хотя бы одного узла и стабилизации запуск возобновляется автоматически; после рестарта scheduler шлюз закрыт до получения состояния (RUN-015, SHD-005).

27. Бэкапы rqlite и логов запускаются по расписанию из scheduler и вручную из единого раздела UI; снимок логов делается на узле без отставания доставки, не останавливает прием и запуск задач; без подходящего узла бэкап откладывается с алертом; политика, история и статусы видны в UI, действия записаны в audit (BKP-001--BKP-003, BKP-006).

28. Потеря тома одного узла VictoriaLogs приводит к автоматическому восстановлению копированием снимка со второго узла (пауза записи порядка секунд), потеря обоих узлов --- к восстановлению из новейшего проверенного бэкапа, без действий администратора; при потере записей диапазон записан в audit и виден в UI; бэкап со статусом `bad` не используется (BKP-004).
