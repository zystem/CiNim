# 0009. ZeroMQ с CURVE как прямой транспорт: замер

- Статус: рассмотрено; выбран NNG (ADR 0010)
- Связанные ID: D-01, D-04, 7.1, 9.2, IAM-003, SEC-001, SEC-010, Q-17 (предложен)
- Решение владельца: шифрование CURVE устраивает, mTLS на X.509 не обязателен для каналов (Q-17, вариант ослабления 9.2).

## Как мерили

libzmq 4.3.5 (C++) и libsodium 1.0.20 собраны из исходников в рабочем каталоге (статические библиотеки, бинарник зонда 0,9 МиБ, динамические
зависимости: glibc, libstdc++). Зонд `tools/m0/zmq_core/probe.c` (одноразовый замер), сервер и клиент отдельными процессами на loopback.

Первая сборка без libsodium молча получила libzmq **без CURVE** (`zmq_curve_keypair` вернул ошибку): в cmake-сборке 4.3.5 CURVE работает
только с libsodium. Ошибка зонда, найденная по ходу: сокеты ZeroMQ не потокобезопасны, отправка и прием одним сокетом из двух потоков
давали «8 из 2000»; после перехода на один поток с `zmq_poll` пришло 2000 из 2000.

Аутентификация клиентов: CURVE шифрует и аутентифицирует пару ключей, но сервер по умолчанию принимает **любой** публичный ключ клиента.
Список разрешенных ключей проверяет ZAP-обработчик (в зонде около 10 строк C). Готового обработчика в самой libzmq нет (он в отдельной czmq).

## Находки и ограничения

1. **Свое в безопасности.** Управление ключами полностью наше: выдача, ротация, отзыв (удаление из списка), распространение списка
   разрешенных ключей всем серверам. Нет CA, cert-manager и сроков действия. Для IAM-003 («bootstrap-токен обменивается на identity»)
   identity становится парой ключей CURVE, выдаваемой при обмене; ZAP-обработчик должен читать актуальный список из состояния шарда.
2. После аутентификации ZeroMQ выражает только «ключ разрешен». Разграничение по каналам и ролям делается нашей стороной
   (отдельные порты и списки ключей для shim, executor, job-контроллера, либо токен в первом сообщении, SEC-010).
3. Обратное давление есть (HWM, блокирующая отправка). По умолчанию ROUTER и PUB отбрасывают при переполнении: для надежных каналов нужны
   `ROUTER_MANDATORY` и малые HWM (E-003: HWM по умолчанию 1 000 сообщений означает до 64 МиБ буфера на соединение при кадрах по 64 КиБ).
4. libzmq на C++, зависит от libstdc++; статический musl-бинарник не получить (Alpine не пробовался). Образ на glibc (`distroless/cc`).
5. Не проверено: поведение при обрывах и переподключении, нагрузка сотен пиров, производительность CURVE на tweetnacl
   (в cmake-сборке недоступен; в autotools-сборке возможен, не пробовалось), musl (Alpine).

## Проверка готовой привязки для Nim (пакет `zmq` 1.5.3)

Тест `tests/integration/tzmq.nim` (Nim 2.2.4, ORC): сервер REP с CURVE и ZAP-обработчик в отдельных потоках, клиенты в главном потоке.
Запуск: `LD_LIBRARY_PATH=<каталог с libzmq.so, собранным с libsodium> nim c -r tests/integration/tzmq.nim`.

| Проверка | Результат |
|:---|:---|
| Компиляция и загрузка под Nim 2.2.4 ORC | работает без изменений пакета |
| CURVE: разрешенный клиент обслужен; обычный клиент, неизвестный ключ клиента, неверный ключ сервера отклонены | да |
| 2 000 запрос-ответ | верно, около 22 600 запросов/с |
| 3 000 циклов connect/close | RSS около 36 Б на соединение, куча Nim +16 Б за все циклы |
| ASan + LSan | 0 отчетов (ни ошибок памяти, ни утечек), выход 0 |

Особенности обертки:
1. Сгенерирована c2nim из заголовков libzmq **4.2.0** (константы совпадают с 4.3.5 для нужных опций). Линкуется через `dlopen` (`libzmq.so(.4|.5|)`),
   поэтому нужна разделяемая libzmq; статическая сборка через нее невозможна.
2. Высокоуровневый API (`listen`, `connect`) привязывает сокет сразу при создании, а опции CURVE надо задавать до `bind`:
   для CURVE годится только низкоуровневый API `zmq/bindings`. Нет ни `zmq_curve_keypair`, ни поддержки ZAP: `importc` одной функции своей строкой и ZAP-цикл (около 30 строк Nim).
3. Для E-003 нужен свой тонкий RAII-тип (`=destroy` с `LINGER = 0` и `close`), в тесте около 10 строк.
   У `ZConnection` в обертке есть `=destroy`, но `=copy` копирует указатель на сокет без владения: риск двойного закрытия, не проверялся.
4. Асинхронный слой обертки (`asynczmq`) построен на `asyncdispatch`; с учетом утечки из ADR 0005 не использовался и не проверялся,
   в сервисах нужны потоки с блокирующими сокетами (сокет привязан к одному потоку).
5. Лицензия: libzmq LGPL-3.0 (со статическим исключением, из памяти, проверить); файл обертки несет заголовок LGPL. Для ядра Apache-2.0 (Q-01)
   динамическая линковка, как здесь, обычно допустима, но формулировку должен проверить владелец.

## Вывод

ZeroMQ лидирует по скорости (923 МиБ/с, 18 697 запросов/с), клиент 4,8 МиБ, утечек нет (проверено и из Nim, и под LSan), готовая привязка для Nim
работает под Nim 2.2.4 (у NNG привязки нет). Цена: собственное управление ключами и ZAP, C++ и только glibc, сокеты привязаны к потоку,
обертка требует низкоуровневого API и своего RAII, лицензия LGPL. NNG лучше по памяти и по стандартной PKI, но требует привязки.
