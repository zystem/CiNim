# 0011. Spike 4: Kubernetes из Nim, Pod на step, shim, хранилище run

- Статус: accepted для клиента, shim и модели хранилища; **RUN-013 не подтвержден** (см. ниже), решение по session mode за владельцем
- Связанные ID: RUN-002, RUN-005, RUN-010, RUN-013, RUN-014, STO-001, STO-003, STO-004, SEC-010, SEC-011, SES-001, NFR-012, Q-11
- Стенд: кластер `admin@home` (Talos, Kubernetes 1.34, 3 control-plane и 3 worker, рабочие узлы для тестов: 2), StorageClass только `directpv-min-io`.

## Решение по клиенту (правило «не писать свое»)

Готового клиента Kubernetes для Nim нет (единственный `wonderix/n8s` заброшен с 2021 года). Взят **официальный C-клиент** kubernetes-client/c (Apache-2.0),
его **generic API** (JSON туда и обратно для любого ресурса: Pod, PVC, Secret, Lease) с готовыми kubeconfig, in-cluster конфигурацией, TLS и потоковым watch.
Привязки к Nim сгенерированы c2nim из его заголовков (`tools/k8s/gen.sh`, модули в `src/common/k8sc/`, линковка в `src/common/k8sbind.nim`),
сборка зависимостей (libyaml, curl с OpenSSL, libwebsockets, клиент) скриптом `tools/k8s/build_client.sh`. `libkubernetes.so` 4,6 МиБ, снаружи зависит только от OpenSSL и libz.

## RUN-013: задержка запуска Pod (не достигнута надежно)

Замер от вызова создания Pod до момента, когда API показывает контейнер запущенным (образ прогрет, restricted-профиль, busybox). Три прогона на общем домашнем кластере:

| Серия | create → контейнер запущен, p50 | p95 |
|:---|:---|:---|
| Последовательно (по одному) | 0,9 / 1,7 / 1,7 с | 1,8 / 2,9 / 7,0 с |
| Пакет из 50 Pod | 8,4–8,7 с | 11,2–11,8 с |
| Последовательно + init-контейнер (доставка shim) | 2,8 с | 6,1–6,6 с |
| Последовательно, `nodeName` задан заранее (без scheduler) | 1,6 с | 3,6 с |

Разбивка: создание → назначение на узел около 0,15–0,25 с (scheduler не узкое место, `nodeName` не помогает); основное время у kubelet
(«назначен → запущен» p50 0,7–1,4 с, хвост до 7 с); статус доходит до API еще на ~1,2 с позже запуска процесса (status manager kubelet),
поэтому метрика по API завышает реальный старт пользовательского процесса. Init-контейнер добавляет около 1 с к медиане и тяжелый хвост.

Выводы: (1) цель p95 не более 3 с выполняется только в удачных прогонах, хвосты до 7 с; (2) меры 1–3 из 7.4 (том, постоянные тома, предзагрузка образов) kubelet не ускоряют;
(3) доставку shim лучше делать монтированием (ConfigMap, лимит 1 МиБ, у нас 150 КиБ), а не init-контейнером; (4) при пакетном запуске на двух узлах задержка 8–12 с:
емкость узлов и kubelet определяют пропускную способность (NFR-006). Стенд общий и шумный, узлов два: для решения по SES-001 (a) нужен повтор на целевом кластере.
Это точка, где владельцу решать, нужен ли session mode (7.4, Q-14).

## Выводы по хранилищу (Q-11 для этого кластера)

RWX недоступен: только `directpv-min-io` (том привязан к узлу, RWO). Все Pod run фактически на одном узле (scheduler делает это сам по topology тома),
параллелизм jobs ограничен ресурсами узла. Потеря узла означает потерю workspace (снапшотов нет), а RUN-014 «повтор после потери узла» без данных невозможен:
нужна политика (перезапуск run или восстановление из артефактов, PIP-015). Пункты (c) RUN-014 (аффинити) обеспечены самим StorageClass, но это свойство именно его.

## Риски и правила, найденные по ходу

1. **ORC и потоки:** нельзя делить между потоками таблицы и строки Nim (потоковые кучи, неатомарные счетчики): падение SIGSEGV в watch-потоке.
   Между потоками передавать только POD-структуры (массив событий под блокировкой), таблицы держать в одном потоке.
2. **Нет таймаута запроса у C-клиента:** один прогон watch в свежем процессе завис на 8,5 минут (не воспроизведен). Таймауты задать через `curl_pre_invoke_func`
   (`CURLOPT_TIMEOUT`, `CURLOPT_CONNECTTIMEOUT`); один `apiClient` на поток, `apiClient_setupGlobalEnv` до создания потоков.
3. Удаление namespace с ~150 завершенными Pod заняло около минуты: cleanup (RUN-005, NFR-004) не мгновенный, GC по меткам `cicd.io/run` должен быть асинхронным.
4. `nil` в ответе `JsonNode{...}` при отсутствии поля: итерация по нему падает; статус Pod приходит по частям, поля появляются позже.

## Решения по парсеру env-файла (уточнить у владельца, E-007)

Спека задает формат не полностью. Принято строго: пустые строки допустимы; строки-комментарии (`#`), одинарные кавычки и escape `\r` **отклоняются**;
глубже deny-list, чем перечислено в STO-004, вошли интерпретаторные и загрузчиковые переменные (`PYTHONHOME`, `NODE_PATH`, `RUBYOPT`, `PERL5OPT`, `JAVA_TOOL_OPTIONS`,
`GLIBC_*`, `DYLD_*`, `BASH_FUNC_*`, `PS4`, `PROMPT_COMMAND` и др.). Список задается в `src/shim/dotenv.nim`.

## Не проверено

Проверка подписи токена на стороне Nim (кандидаты `jwt`, `quickjwt`, `jwtea`, C-библиотека `libjwt` с поддержкой JWKS; проверено только независимым PyJWT);
NNG-канал от shim к collector и StepReport (следующий срез); потоки логов и redaction в shim; in-cluster конфигурация клиента (проверен kubeconfig);
статическая сборка контроллера на musl; PVC с `WaitForFirstConsumer` и потерей узла; NetworkPolicy и restricted Pod Security на namespace профиля (проверялись лишь поля Pod);
поведение при 500 одновременных Pod (NFR-003), потеря узла, отзыв токена, доставка shim через image volume (K8s 1.34).
