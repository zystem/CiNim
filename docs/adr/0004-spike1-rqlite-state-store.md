# 0004. Spike 1: rqlite как хранилище состояния шарда

- Статус: accepted, go с оговорками (ниже)
- Связанные ID: D-02, 7.2, 7.3, RUN-002, NFR-003, NFR-006, `[M0-CHECK]`
- Стенд: ADR 0002 (rqlite v10.3.5, 3 узла, Talos, PVC directpv). Тесты: `tests/integration/trqlite.nim`,
  клиент `src/common/rqlite.nim`, помощники `tools/m0/pf-follower.sh`, `tools/m0/leaderkill-soak.sh`.

## Результаты

| Проверка | Результат |
|:---|:---|
| Постановка step: `UPDATE ... WHERE id=(SELECT ... LIMIT 1) ... RETURNING` | Работает; 300 step, 8 конкурентных клиентов: каждый step получен ровно один раз, ни одного двойного захвата |
| CAS `WHERE version=?` | Из двух гонящихся записей побеждает ровно одна (`rows_affected` 1 и 0) |
| Транзакция «состояние + пакет журнала» | Атомарна: при ошибке в последнем выражении откатывается весь пакет |
| Пакетирование | 500 строк в запросе: около 4 000 строк/с против около 15 одиночных записей/с (через port-forward): разница ~260× |
| Задержка одиночной записи | ≈40 мс на лидере (внутри pod'а около 25 записей/с последовательно), 70 мс через port-forward и follower |
| VACUUM на ~20 МБ при непрерывной записи | Записи блокируются: худший простой 1,1–2,6 с (p99 равен максимуму), p50 50–100 мс |
| Убийство лидера (`--force --grace-period=0`) во время записи | 20 прогонов серии плюс 15 ранее: 0 потерянных подтверждённых записей (5 821 подтверждённых в серии); провал доступности записи 0,13–1,6 с, медиана 0,24 с |

## Находки

1. **200 не значит успех.** При смене лидера rqlite отвечает HTTP 200 с телом `{"results":[],"error":"leadership transfer in progress"}`.
   Клиент обязан проверять `error` верхнего уровня и `error` каждого результата; иначе неудачная запись выглядит подтвержденной
   (так родился ложный «потерянный ack» в первом прогоне). Исправлено в `rqlite.nim`, регрессия проверяется тестом.
2. `rows_affected` не приходит в JSON, когда равен 0.
3. Постановка по одной строке выдает ≈60 захватов/с на набор клиентов. Для NFR-003 (p95 < 2 с при 500 одновременных step)
   scheduler должен забирать пачку step одним `UPDATE ... LIMIT n RETURNING` и группировать записи (7.3, лестница пункт 1).
4. VACUUM и snapshot останавливают запись на секунды: их нужно планировать вне пиков (7.3), а хранить в rqlite только состояние.
   Пороги snapshot по умолчанию: 8192 записи лога или 10 с. Остановка именно при snapshot отдельно не измерялась.

## Не проверено

Все замеры идут через `kubectl port-forward` и один кластер из трех узлов на общих дисках directpv, поэтому абсолютные задержки завышены
относительно цели. Не проверено: нагрузка 1 000 одновременных step (NFR-006), non-voting узлы для чтения, уровни чтения `weak`/`none`
со свежестью, потеря узла с диском (восстановление), сетевые разрывы между узлами.

## Решение

Go: rqlite подходит как источник истины при условиях: пакетная запись и постановка пачками, обязательная проверка ошибок верхнего уровня,
snapshot/VACUUM вне пиков, повтор запросов клиента при смене лидера. Условие пересмотра D-02 (цель одного шарда не достигается)
остается, проверка NFR-006 переносится в M1.
