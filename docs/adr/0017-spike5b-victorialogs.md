# 0017. Spike 5b: VictoriaLogs как LogStore (100 млн строк, HA, бэкап, live tail)

- Статус: результаты приняты; **go**. Меняет D-07, D-20, D-21, DAT-008, DAT-010, DAT-011, ZF-1..ZF-8 (ZincSearch и его форк из контура логов выходят)
- Связанные ID: NFR-005, NFR-012, NFR-015, BKP-001..006, RUN-015, SHD-005; ADR 0014, 0016
- Как мерили: локально в Docker, VictoriaLogs v1.52.0 (Apache-2.0), vlagent v1.52.0, vmauth; те же CI-подобные строки, что в ADR 0014/0016.
  Скрипты: `tools/m0/logstore/{ha_test.py,scale.sh,scale_q.py,misc_q.py}`.

## Что найдено о продукте (документация, флаги бинарника)

- **Реплики в хранилище нет.** Кластерный режим (vlinsert/vlstorage/vlselect) шардирует, но не реплицирует; запросы возвращают 502, пока недоступен любой vlstorage; mTLS только в enterprise.
  Поэтому HA строится так, как рекомендует документация: **два независимых одиночных узла**, которые кормит **vlagent** (готовый агент с дисковым буфером на каждый адрес назначения), чтение через **vmauth** (`first_available`).
- Снимки: `POST /internal/partition/snapshot/create|list|delete`, восстановление копированием каталога раздела (`rsync`/`cp`). Готового `vlbackup` в открытой редакции нет (выгрузка в S3 обычным инструментом, например `rclone`; не проверялось).
- Удаление: `-delete.enable`, `POST /delete/run_task?filter=...`; хранение по времени `-retentionPeriod` и по месту `-retention.maxDiskSpaceUsageBytes` **общие для всего узла**, отдельного срока на тенанта/поток нет.
  Разделы по дням (`partitions/YYYYMMDD`), их можно отсоединять и удалять.
- Мультитенантность встроена: заголовки `AccountID`/`ProjectID` (тысячи тенантов без накладных расходов).
- Транспорт: `-tls`, `-httpAuth.*` (логин и пароль), у клиента vlagent TLS и учетные данные; **клиентские сертификаты (mTLS) только в enterprise**. Схема совпадает с решением для NATS: TLS плюс логин/пароль внутри шарда.

| Диск | 3 563 МиБ на 9,2 ГиБ текста = **0,39×** | ≤ 3× |

| Редкий токен в потоке 1 млн строк / по всем 100 млн | 105 мс / 586 мс | — |

### HA: два узла, vlagent, vmauth (по 2 млн строк на этап)

| Проверка | Результат |
|:---|:---|
| Оба узла получают данные через vlagent | счётчики равны через 2 с |
| Узел B остановлен, идёт запись 2 млн строк, B запущен | счётчики сошлись за **6,6 и 18,7 с** (два прогона), потерь и дублей нет (4 000 000 = 4 000 000); буфер vlagent опустел (24 КБ) |
| Чтение через vmauth, A убит | **ни одной неудачной проб-заявки** (повтор на B по `retry_status_codes`), счёт через vmauth верен |
| Потеря диска A: пауза агента, снимок B (0,02 с), копия в A (0,13 с на 143 МиБ), очистка очереди A в агенте, запуск | A стартует с 4 000 000 строк, **общая пауза записи 1,5 с**, после возобновления и 200 тыс. новых строк счётчики равны, окно на A и B побайтно совпадает |

Порядок восстановления важен: очередь vlagent для A нужно очистить (иначе строки, попавшие и в снимок, и в очередь, задваиваются: дедупликации в VictoriaLogs нет).
Запись на время восстановления приостанавливается (для 100 млн строк копия ≈ 3,5 ГиБ: десятки секунд); шлюз запуска RUN-015 уже умеет закрывать запуск на это время.

## Что меняется в архитектуре

1. Контур логов: **collector → vlagent (два узла VictoriaLogs) → vmauth → gateway**. Исчезают: форк ZincSearch, coordinator (D-21, порт на Nim не нужен), потоки JetStream для логов и вопросы NATS mTLS.
   NATS остается только для событий платформы (7.3), если будет нужен.
2. Роль coordinator сводится к: проверке здоровья двух узлов (vmauth уже переключает чтение), процедуре восстановления узла (пауза агента, снимок с живого узла, копия, очистка очереди, запуск), снимкам по расписанию с выгрузкой в S3 и удалению по retention.
   Это скрипты и вызовы HTTP, а не отдельный сервис; логику решений (шлюз RUN-015: узел жив и очередь vlagent небольшая) пишет core на Nim (метрики vlagent: `vlagent_remotewrite_pending_data_bytes`).
3. Ключ окна: время строки `_time` с миллисекундной точностью; для порядка внутри одной миллисекунды и просмотра «по номеру строки» хранить `ln` полем и сортировать по `(_time, ln)`. Проверить: строки с равными метками времени (collector может назначать монотонное время `base_ts + ln` внутри job).
4. Retention на тенанта и на тип данных: `-retentionPeriod` общий; для разных сроков использовать удаление по фильтру (`delete/run_task`, 8 с на 1 млн строк) или отдельные экземпляры.

## Не проверено

- Запись через vlagent на 100 млн строк и его память/CPU; буфер vlagent при долгой (часы) недоступности узла и лимит `-remoteWrite.maxDiskUsagePerURL`.
- Выгрузка снимков в S3 и восстановление из S3 (rclone); `verify` аналог `verify-backup --deep`: проверять открытием снимка на отдельном узле.
- TLS и логин/пароль на цепочке vlagent → узлы и gateway → vmauth → узлы; `-httpAuth` для внутренних `/internal/*`.
- Точный порядок и задержки при разрыве сети (split brain: vlagent доставляет обоим, узлы независимы, расхождение только по недоставленным строкам).
- Утечки и рост памяти под soak (NFR-013) для vlagent, VictoriaLogs, vmauth; лимиты памяти узла (`-memory.allowedBytes`).
- Несколько тенантов с большими объемами одновременно; многодневные разделы (тестовые данные лежат в одном дне).
- Redaction (DAT-002) остается в collector до записи.
