# 0008. NNG (C) как прямой транспорт между сервисами: замер

- Статус: рассмотрено; выбран NNG (ADR 0010)

## Как мерили

NNG 1.12.4 и mbedTLS 3.6.2 собраны из исходников в рабочем каталоге: один раз динамически с glibc и один раз статически с `musl-gcc`.
Нативный зонд `tools/m0/nng_core/probe.c` (одноразовый замер): сервер и клиент отдельными процессами на loopback, mTLS с общим CA
(`tests/certs`). Паттерны: REQ/REP (запрос-ответ, оборот соединений), PUSH/PULL (поток как shim → collector), PAIR полиаморный (двунаправленный).
Первый прогон показал «рост клиента 12,8 КиБ на соединение»: это была ошибка зонда (новый TLS-конфиг и неосвобожденные буферы PEM на каждой итерации),
после исправления рост нулевой; на такие ошибки зондов стоит смотреть при любом «росте».

## Находки и ограничения NNG

1. **PAIR теряет сообщения при перегрузке**: 190 из 2 000 в пачке дошли, порядок нарушен (очереди ограничены, лишнее отбрасывается).
   Для надежной доставки использовать REQ/REP и PUSH/PULL (у PUSH/PULL есть обратное давление: 256 МиБ дошли полностью).
   Двунаправленный надежный канал выражается парой сокетов PUSH/PULL в разные стороны или REQ/REP; роль сокета не зависит от того,
   кто слушает, а кто подключается (job-контроллер подключается наружу и может быть REP-стороной).
2. Привязки к Nim нет (пакет `nanomsg` относится к старой библиотеке без TLS). Нужна тонкая привязка к небольшому C API
   (около десятка функций); по правилу владельца через готовый генератор (`futhark`, нужен libclang; не проверялось).
3. Не проверено: идентичность клиента из сертификата в приложении (в NNG есть опции пира TLS, надо проверить `NNG_OPT_TLS_PEER_CN`),
   размеры сообщений и лимит приема (задать `NNG_OPT_RECVMAXSZ`, E-003), нагрузка сотен одновременных соединений,
   ASan/LSan, повторное подключение и поведение при обрыве, поставка обновлений mbedTLS (безопасность), совместимость с плагинами на других языках
   (привязки к NNG есть для Go, Rust, Python, но не везде так зрелые, как gRPC).
4. Нет gRPC-совместимости и стандартных инструментов (grpcurl и т. п.); отладка своим клиентом.

## Рекомендация

По измерениям NNG выигрывает у остальных: самый малый клиент (1,3 МиБ статически), нет утечки, нет брокера, статический musl-бинарник,
mTLS на сертификатах. Его цена: привязка к Nim через генератор и нестандартный протокол вместо gRPC.
Если владелец хочет стандартность и совместимость с внешними клиентами, остается gRPC C-core (ADR 0006).
Если хочет брокер (события, логи через JetStream) — NATS (ADR 0007). Гибрид NATS для событий и логов плюс NNG для каналов с fencing
в этом сравнении выглядит разумнее, чем NATS плюс gRPC, если стоимость поставки gRPC (52 библиотеки, только glibc) неприемлема.
