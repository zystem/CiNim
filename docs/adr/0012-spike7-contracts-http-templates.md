## 1. `.proto` v0

Файлы `proto/cicd/internal/v1/*.proto` (общие типы, ControllerAttach, LogIngest, StepReport, ExecutorChannel, Directory и ClusterState) и `proto/cicd/plugin/v1/plugin.proto`
(по PLG-008). Каналы записаны в терминах NNG (ADR 0010): контроллер опрашивает scheduler запросом-ответом (пакет подтверждений, событий и команд), shim шлет пакеты
чанков лога и получает подтверждение после записи в JetStream, executor делает один запрос на вызов host API. Это предложение схемы каналов из ADR 0010, фиксируется тестами на потери и обрывы в M1.

Проверки: `buf lint` (STANDARD) и `buf build` проходят; `tests/contract/tproto_v0.nim` сверяет кодек Nim с эталоном (Python на коде `protoc` из тех же файлов):
кодирование побайтно там, где порядок полей совпадает, декодирование и повторное кодирование всех векторов, oneof, map, `Timestamp`, `bytes`, `fixed32`, пропуск неизвестных полей будущей версии.
`tests/contract/tproto_compat.nim` проверяет N/N-1 через `buf breaking` против образа предыдущего релиза `proto/compat/baseline.binpb`:
добавления проходят, удаление и смена типа и номера поля, удаление enum-значения и сообщения ловятся.

Находки:
1. Кодек Nim **не компилирует рекурсивный `google.protobuf.Struct`** (`Value`, `Struct`, `ListValue`). Для Nim контракт плагина сплющивается со Struct-полями как `bytes` с теми же номерами полей
   (`tools/proto/nim_flatten.sh`); байты на проводе те же, плагины на других языках работают по исходному `.proto`.
2. `import_proto3` разрешает не-google импорты относительно каталога файла, а `buf` требует пути от корня модуля: для Nim делается плоская копия с переписанными импортами (одна строка `sed`).
3. **Порядок полей на проводе не совпадает** между Nim (порядок объявления) и `protoc` (по номерам). Побайтовое равенство между реализациями не гарантируется:
   хеши журнала считаются по каноническому JSON полей `payload` и `result`, а не по байтам Protobuf; подписывать сериализованный Protobuf нельзя.

## 2. State machines

`src/common/states.nim` (таблицы переходов: run, step, шлюз запуска, input), `docs/state-machines.md` генерируется из них (`nim r tools/gen_state_docs.nim`), тесты `tests/unit/tstates.nim`:
терминальные состояния финальны, все состояния достижимы, из любого нетерминального состояния можно отменить и завершить, `waiting` только из `running`, `lost` только из `starting` и `running`,
`starting -> pending` только пока нет Pod (условие в том же CAS), имена совпадают с `RUN_STATE_*` и `STEP_STATE_*` в `common.proto`.

Несоответствие спеки: состояния step в RUN-001 (`pending`, `starting`) и в SQL-примере 7.2 (`queued`, `dispatched`). Принято соответствие: **pending = queued, starting = dispatched**;
в rqlite хранятся имена из RUN-001, а `dispatched` в запросе постановки читается как `starting`.

## 4. HTTP-слой: civetweb

Требования: потоковый ответ без сборки страницы в памяти (UI-009), SSE (UI-004), потоковая выгрузка лога с постоянной памятью (DAT-009), бюджет памяти (NFR-012), отсутствие утечек.

| | civetweb 1.16 (C, MIT, Nim-привязка c2nim) | mummy 0.4.8 (Nim, потоки) | httpbeast 0.4.1 (Nim, async) |
|:---|:---|:---|:---|
| Простой RSS | 4,1 МиБ | 2,5 МиБ | 2,2 МиБ |
| Рост после 20 тыс. запросов keep-alive | +0,4 МиБ, дальше ровно | +0,7 МиБ, дальше ровно | не измерен (см. ниже) |
| 5 000 новых соединений | +8 КиБ | +16 КиБ | +0 |
| 20 000 ответов 500 из обработчика | +100 КиБ | +140 КиБ | **процесс завершился** на первом необработанном исключении |
| Потоковый ответ, SSE | да (chunked, SSE), 256 МиБ потоком при плоских 4,7 МиБ, медленный читатель тоже | **нет** (только целиком, WebSocket) | нет обратного давления |
| Запросов/с, страница из 100 строк | 11 тыс. (102 чанка на ответ) | 45 тыс. (целиком) | не сопоставим |
| Модель | пул потоков C, обработчики на Nim (`{.cdecl.}`) | потоки | async, исключения убивают процесс |

Решение: **civetweb** для UI/API и log gateway. Правила: обработчик перехватывает все исключения и не выпускает их через C-фрейм; между потоками только простые данные (ADR 0011);
рендер частями (заголовок, строки, подвал) и отправка `mg_send_chunk`. Скорость страницы можно поднять склейкой чанков (не делалось). TLS для внешнего UI завершается на ingress; civetweb собран с OpenSSL,
если понадобится собственный TLS или проверка клиентского сертификата. `darkhttpd`/`promlite` (ваши проекты) остаются кандидатами для `/metrics` и статики.
Не проверено: ASan/LSan на процессе civetweb (сервер не завершается штатно в замере), WebSocket, лимиты размера тела и заголовков (опции civetweb).

## 5. Шаблонизатор: nimja с принудительным экранированием

`nimja` компилирует шаблоны при сборке (около 10 мкс на страницу из 100 строк, тысячи запросов в секунду на поток) и **не экранирует HTML автоматически** (проверено: `<script>` выводится как есть).
`mustache` (готовый пакет) экранирует по умолчанию, но рендерит ту же страницу 2,5 мс (в 250 раз медленнее). Решение: `nimja` плюс явные `{{ h(x) }}` (экранирование) и `{{ raw(x) }}` (доверенный HTML, например SVG);
`src/ui/render.nim`, шаблоны в `src/ui/templates/*.nimja`, тест `tests/unit/ttemplates.nim` проваливает сборку на любом выражении вне `h(...)` и `raw(...)` и проверяет рендер с враждебными данными.

## Открытые вопросы (владельцу)

1. **Q-18: идентичность shim.** Спека требует mTLS на всех каналах, но сертификат получает только job-контроллер, у Pod step есть токен задания (SEC-010). Предложение: сервисы и контроллер по mTLS,
   shim по TLS с проверкой сервера плюс токен на каждом сообщении.
2. **PLG-008:** оставить `google.protobuf.Struct` (для Nim как `bytes`) или заменить на строку JSON.
3. Внешний TLS на ingress (подтвердить).
