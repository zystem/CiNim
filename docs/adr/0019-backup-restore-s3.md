## rqlite: `-auto-backup` / `-auto-restore`

**Находка: писать свой инструмент бэкапа не нужно.** У rqlite есть встроенные флаги `-auto-backup` и `-auto-restore` с
JSON-конфигом (`type: s3`, `interval`, `sub: {access_key_id, secret_access_key, endpoint, region, bucket, path,
force_path_style}`), документированы на rqlite.io. Бэкап делает **только лидер** (при смене лидера подхватывает новый);
он же **не делает бэкап без изменений** (проверяет, отличаются ли данные, перед загрузкой). Восстановление происходит на
старте узла, до входа в кластер. Официальный chart `rqlite/rqlite` поддерживает это без доработок через `extraArgs` и
`extraFiles` (JSON-файл монтируется, путь передаётся флагом).

| Проверка | Результат |
|:---|:---|
| Автозагрузка в S3 (интервал 20 с, тест) | каждая загрузка 6--17 мс, кроме первой (507 мс: сравнение с несуществующим объектом) |
| Влияние на запись во время загрузки | **не выявлено при чистом стенде** (300--800m cpu на под): p50 11,6 мс, p95 18,5 мс на 5000 записей за 2 мин, без всплесков, привязанных ко времени загрузки. При зажатом лимите CPU (100m) на самом тестовом поде --- сильный шум (p95 до 80 мс), но он не совпадает по времени с моментами загрузки бэкапа; это троттлинг тестового пода, не бэкап. Вывод ADR 0004 про VACUUM (простой 1,1--2,6 с) бэкапа не касается: сама операция на два порядка быстрее |
| Восстановление в чистый узел (`-auto-restore`, тот же S3-путь) | `node loaded in 7.9 ms (198 bytes)`; узел стал лидером и отдаёт данные через 1 с после старта |
| RPO (потеря узла между бэкапами) | **измерено точно**: бэкап в T, 5 записей после T, узел уничтожен в T+13,5 с --- восстановленное состояние равно T (потеряны ровно эти 5 записей, ни одной лишней). RPO = интервал автобэкапа |

Вывод: BKP-005 не нуждается в собственном инструменте и команде `cicd admin restore-state` как отдельной разработке ---
это конфигурация двух флагов rqlite. Восстановление в кластер (не единственный узел) не проверялось: по документации
только один узел (обычно тот, что становится лидером) реально применяет `-auto-restore`, остальные получают данные через
Raft; это стоит подтвердить отдельно на 3-узловом кластере.

## VictoriaLogs: RPO при потере обоих узлов

Сценарий: узел вне кластера (представляет оба узла шарда, потерянных одновременно), 20 000 строк, снимок раздела,
выгрузка снимка в S3 (`mc mirror`, эмулирует контейнер-компаньон rclone из DAT-010/BKP-003), ещё 3 000 строк «дрейфа»
после снимка, полное уничтожение пода (эквивалент потери обоих узлов и их томов), восстановление в новый под: init-контейнер
скачивает снимок из S3 в `<-storageDataPath>/partitions/<раздел>/` **до** старта VictoriaLogs, затем узел стартует как
обычно и сам подхватывает раздел с диска.

| Проверка | Результат |
|:---|:---|
| Снимок раздела | 0,02 с (совпадает с ADR 0017) |
| Выгрузка в S3 (`mc mirror`, 20 000 строк, 128 КиБ) | <1 с |
| Уничтожение узла --- новый под Running | 16 с (маленький объём; время должно расти с размером снимка, ADR 0017 давал 143 МиБ за 0,13 с на копирование, то есть узкое место --- сеть/диск, не логика) |
| Восстановленные данные | ровно 20 000 строк «до снимка», **0** строк «после снимка» (полное совпадение с ожиданием, без лишних и без потерянных внутри окна) |

Вывод: RPO логов при потере обоих узлов равен интервалу снимка (по умолчанию 1 ч, BKP-001), как и заявлено в DAT-010;
механизм восстановления (init-контейнер копирует раздел до старта) работает и не требует API `attach`/`detach`
(они нужны только для узла, который уже запущен). Оба узла реального шарда синхронизированы через vlagent и обычно имеют
одинаковые данные (ADR 0017), поэтому в реальности снимок можно брать с любого доступного узла в момент потери --- этот
путь (снимок с живого узла прямо в момент отказа второго) не проверялся отдельно.

## Не проверено

Восстановление `-auto-restore` в многоузловом кластере rqlite (только на одном узле проверено); проверка контрольной
суммы против манифеста (BKP-006 для обоих типов бэкапа --- здесь просто сверили число строк/значение счётчика, не
криптографическую сумму); поведение при повреждённом (не просто отсутствующем) бэкапе; частота реального интервала (1 ч)
не воспроизводилась, использован короткий интервал (20 с) для скорости теста; лицензионные и стоимостные вопросы
реального S3 (тестировали на MinIO, не на настоящем облачном S3).
