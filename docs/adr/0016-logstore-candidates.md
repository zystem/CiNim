# 0016. Замена LogStore: сравнение кандидатов

- Статус: **принято владельцем: VictoriaLogs** (2026-09-22); проверка репликации, бэкапа и 100 млн строк в ADR 0017
- Связанные ID: D-07, D-20, DAT-007..011, ZF-7, ZF-8, NFR-005, NFR-012, NFR-015; ADR 0014
- Условие владельца: Elasticsearch не рассматривается (память).
- Как мерили: `tools/m0/logstore/{gen.py,bench.py,runall.sh}`, один кандидат за раз в Docker (последние образы на 2026-09-21), 5 млн строк = 5 job по 1 млн,
  459 МиБ текста, такие же CI-подобные строки, как в ADR 0014. Приём одним потоком Python (~90 тыс. строк/с: это предел драйвера, не хранилищ). Локально, не на стенде.
  Сырой вывод: `docs/adr/data/*.out`.

Ключ окна: у VictoriaLogs и Loki это время (`_time` = метка строки, порядок строк сохраняется по возрастанию), у Quickwit и ClickHouse поле `ln` (быстрое поле / первичный ключ `(job, ln)`).
Все окна вернули ровно столько строк, сколько запросили, на случайных смещениях.

## Выводы

1. **VictoriaLogs**: диск в 8 раз меньше ZincSearch с полнотекстовым индексом, окно 6 мс, поиск встроен и быстрый, приём в 10+ раз быстрее индексации ZincSearch, один бинарник на Go.
   Память 427 МиБ на 5 млн строк, кэши ограничиваются `-memory.allowedPercent`. Подходит под NFR-005 и NFR-012 лучше всех кандидатов.
2. **ClickHouse**: лучший по стабильности окна и запросам, но самая большая память (0,8–1 ГиБ уже в простое) и сложная эксплуатация; поиска по тексту без доп. индексов нет (сканирование по job).
3. **Quickwit**: быстрый приём, поиск и подсчет, но окно по `ln` в 8× медленнее (50 мс, всё ещё в пределах 100 мс), 530 МиБ, отдельные компоненты (метаданные, WAL).
4. **Loki**: 4% строк невидимы до flush (head-блок), редкий токен 1,5 с, лицензия AGPL, окно по времени. Не подходит для поиска по строке.

## Не проверено (нужно до решения)

- **Репликация и failover.** Одиночный VictoriaLogs не реплицируется; кластерный режим (vlinsert/vlstorage/vlselect, репликация записи) не мерился. В ZincSearch это решали JetStream и coordinator (D-21). Если репликация VictoriaLogs подходит, coordinator и NATS для логов не нужны, а D-21 отпадает.
- **Бэкап и восстановление** (BKP-*): возможности зависят от редакции (в открытой доступны снимки каталога, проверить порядок восстановления).
- 100 млн строк, много job одновременно, потеря узла, retention по job/тенанту (`delete_index` аналога нет: удаление по времени/потоку), права доступа (без JWT: gateway единственный клиент), апгрейды, live tail (опрос хвоста по `_time`), стабильность памяти под soak.
- Поле `ln`: в VictoriaLogs окно идет по времени; при дублях меток времени внутри job нужен tie-break (поле `ln` хранится, сортировка по `(_time, ln)`).
