# 0006. Транспорт: готовый gRPC C-core или hyperx

- Статус: рассмотрено; выбран NNG (ADR 0010)
- Связанные ID: D-01, D-04, 7.1, NFR-012, NFR-013, ADR 0005
- Правило владельца: не писать свой код, если есть готовый вариант (см. память проекта).

## Что измерено

Клиент: нативная C-программа `tools/m0/grpc_core/rss_client.c` (одноразовый замер) на установленном `libgrpc-dev` 1.51.1 (Debian).
Сервер и функциональные проверки: готовый `grpcio` 1.84 (Python, свое встроенное ядро) с сырыми байтами, без протокольного кода
(`tools/m0/grpc_core/server.py`, `client.py`). Версии ядра различаются, для порядка величин это допустимо, но не для точных чисел.

| Показатель | gRPC C-core | `hyperx` + наши патчи (ADR 0005) |
|:---|:---|:---|
| mTLS: без сертификата, чужой CA клиента, недоверенный сервер | все три отклонены | все три отклонены |
| Двунаправленный стрим, 2 100 сообщений | в порядке | в порядке |
| 256 МиБ одним потоком | 477 МиБ/с (Python-сервер, +24 МиБ RSS сервера) | 47–74 МиБ/с, RSS ровный |
| Рост памяти на соединение (5 000 подключений) | +16…110 Б, затухает, нативный клиент 15,8 → 16,8 МиБ; сервер ровный | клиент 7,2 → 9,2 МиБ; сервер 830 Б/соединение (release), 8 КиБ (debug) |
| RSS клиента после первого mTLS-вызова | **15,8 МиБ** (8,1 МиБ до `grpc_init`: отображение 52 динамических библиотек) | 7,2 МиБ |
| Зависимости | `libgrpc.so` 5,5 МиБ + 51 библиотека (abseil, re2, cares, upb, libstdc++, ssl), 13 МиБ на диске | вендоренные исходники + hpack |
| Статические бинарники | нет: `libcares.a` не установлен, а glibc-static все равно требует динамический glibc для `getaddrinfo` и `dlopen` | да (glibc или musl) |
| Трейлеры `grpc-status`, дедлайны, совместимость с grpcurl и Go/Python-клиентами плагинов | есть из коробки | нет, надо дописывать |
| Свой код | тонкая обертка над C API | патчи в стороннем коде + кадрирование + недостающий gRPC |

## Выводы

1. Ядро решает утечку из ADR 0005 (она в async-слое Nim, которого в C-core нет) и снимает недостающий gRPC.
2. Цена: shim 15,8 МиБ против цели NFR-012 «менее 15 МиБ» (с запасом на сам shim не хватает), образ на glibc (`distroless/cc`, не `scratch`)
   с 52 библиотеками, старая версия ядра из дистрибутива.
3. Не проверено: привязка к Nim (`grpc/grpc.h` через готовый генератор биндингов вроде `futhark`, ручной обертки быть не должно),
   серверная часть и стрим через C API из Nim, сборка на musl (возможно через Alpine `grpc-dev`, не пробовалось), снижение RSS настройками ядра,
   ASan/LSan вокруг C-core.

## Варианты

A. Перейти на gRPC C-core; `hyperx`-патчи и `pbframe` не нужны, кодек Protobuf остается (`protobuf_serialization`, ядро принимает сырые байты).
   Условия: решить бюджет shim (например 20 МиБ) и способ поставки (glibc или Alpine musl).
B. Остаться на `hyperx` и чинить утечку (ADR 0005, варианты 1 и 2); gRPC-трейлеры дописать самим. Противоречит правилу «не писать свой код».
C. Гибрид: gRPC C-core для сервисов шарда (долгоживущие соединения, где 16 МиБ терпимы), `hyperx` не использовать вообще.

Рекомендация: A, после проверки привязки к Nim через готовый генератор (следующий шаг, небольшой).
