# Working on CiNim (notes for a coding session)

Read `README.md` first (what works, the structure, the build), then `docs/specification.md` for a requirement you touch (IDs like `PIP-012`, `DAT-003`, decisions `D-xx`).

## Rules of the project

- Tests first; the name of a test contains the ID of the requirement it verifies. All unit and integration tests, in parallel, about 2 minutes: `tools/test/run.sh` (`-j 8` workers by default, more gains little; every worker has its own rqlite in a Docker container, made new at each run;
  `-u`/`-i` only unit/integration; `tm1skeleton` needs the Kubernetes client and a cluster: name it on the command line). `nimble test` runs the unit tests in turn (about 5 minutes). Run a single file with
  `nim c -r --hints:off --warnings:off --outdir:build/tests tests/unit/<file>.nim`.
- Text in the repository is English. Docs and answers to the owner are in Russian; `docs-tr/` is the owner's gitignored Russian mirror of `docs/` (not in git: update it
  when a doc changes if it exists on your machine).
- The repository holds no private addresses, host names, cluster names or tokens: write "the TESTING cluster" in docs. Real values live in the owner's environment.
- Commit and push only when asked (a stop hook may ask for it). Never `pkill -f` (use `pkill -x name` or a PID). Never ask the owner to paste a token into the chat.
- Hooks (`.claude/settings.json`, scripts and their test in `.claude/hooks/`): a `PreToolUse` guard refuses `pkill -f`, `kubectl`/`helm` that name no cluster, the self-truncating file write, and edits of `tests/certs`, the `docs-tr` stamp and `build/`, and asks before `git commit`/`git push`; a `Stop` hook sends the session back once when `docs/` changed and `docs-tr` is stale, when `proto/` changed and `build/nimproto` is older, or when a tracked file became empty. Check them with `.claude/hooks/test-hooks.sh`.
- The test cluster is for tests: anything may be created and deleted there. The owner decides what is a design change; a doubt about the design is a question, not a guess.
- Report what was checked and what was not. A claim about the code is checked in the code before it is made.

## Building

- Nim 2.2.4 (ORC), `nimble install -d`. System: libzmq, libsodium (`libsodium-dev`; tests of modules that import `src/common/sodiumaead.nim` link `-lsodium`), libpcre (the UI templates).
- `tests/unit/tkekclient_tls.nim.cfg` (`-d:ssl`) belongs to the TLS test; `tools/kekd-emu/certs.py` and `tls-front.py` need Python 3 with `cryptography` and `ssl`.
- The shim has two builds: without `-d:shimLogging` (no ZeroMQ, what the unit tests use) and with it (the real one). Check both: `nim check -d:shimLogging src/shim/shim.nim` and without.
- The job controller needs the Kubernetes C client (`-d:k8sPrefix=...`); without it use `nim check -d:k8sPrefix=/opt/k8s src/jobcontroller/main.nim` to type-check only.
- After a change to `proto/`: `tools/proto/nim_flatten.sh build/nimproto`.
- Quick iterations: `REGISTRY=<host> tools/image/build-local.sh <tag> core storage ...` builds on the workstation with a persistent Nim cache and pushes with `skopeo` (seconds after a change; docs/deployment.md). Releases and anything that must not depend on this machine: the build Pod.
- Images are built in the cluster with `REGISTRY=<host:port as the Pods reach it> TAG=<tag> tools/image/kaniko-build.sh` (both images; Kaniko runs as a build Pod, it needs a few minutes; the script's own
  `kubectl logs -f` may time out before the build ends: wait for the Pod `kaniko-images` in `cinim-build` to be `Succeeded`). Roll out: scale the executor to 0, `kubectl set image` for the core and the
  executor, `CINIM_CONTROLLER_IMAGE` on the core, the controller's image in the organisation's namespace, then the executor back to 1 (two executors on one run during a rollout cause trouble).

## Things that cost time (do not repeat)

- A segmentation fault with no trace in the shim or a thread: iterate a possibly-`nil` `JsonNode` only through `.elems` after a `kind` check. `for x in items(node)` always picks the iterator of `std/json`,
  whatever a function of your own with that name does. Build with `--stackTrace:on --lineTrace:on` and run the binary locally; it shows the line.
- `declared` is a magic of Nim: do not name a proc or a constant so. `func` cannot call `parseJson` (side effects): use `proc`.
- `std/net` `recv(pointer, size, timeout)` insists on all `size` bytes even on an unbuffered socket: wait with `poll` and `recv` without a timeout (`src/shim/artifacts.nim: readSome`).
- A string made in one thread and freed in another crashes tests that use threads: use fixed arrays for what crosses.
- Tools that write a file from itself (`open(p,'w').write(open(p).read())`) truncate it. Edit with a script that reads first, check `git diff --stat` before a commit.
- Integration tests (`CINIM_RQLITE_URL`) need a scratch rqlite; `tools/test/run.sh` starts them in Docker (RAM-backed, faster than a port-forward). By hand: `docker run -d -p 127.0.0.1:24600:4001 --tmpfs /rqlite/file:rw,size=512m,mode=1777 rqlite/rqlite -fk -disco-mode=`. Against a cluster: one node, 1Gi (`helm install rqlite rqlite/rqlite --version 2.0.0 --set replicaCount=1,persistence.size=1Gi`) and a port-forward to the Pod (`pod/rqlite-0 24555:4001`), not to `svc/rqlite`: through the Service the requests hang. A test that makes tables of its own gives them its own names (`bench_...`): the schema's names belong to the other tests.
- The kube API proxy eats the `Authorization` header: reach the core API through a port-forward or an Ingress.
- The controller does not use Kubernetes `exec` (its C client returned nothing in the TESTING cluster, Kubernetes 1.36; D-55); what a step Pod could not deliver is on the run volume and a drain Pod delivers it.
- After `helm upgrade` delete the conductor Pods only when the old controller Pods are gone from the list (`rollout status` answers while they still terminate and make a Pod from the old plan); from then on a conductor of another image is drained by the core by itself.
- Make every HTTP server with `newService` of `src/common/httpsrv.nim`, not with `newHttpServer`: GuildenStern 9.0.1 looks for `content-length: ` in the whole receive buffer of a thread, finds the header of an earlier POST behind the end of a shorter request and closes the connection, so a third of the connections were dropped after a few dozen POSTs (and `kubectl port-forward` died at the first). `tests/integration/thttp.nim` fails without the fix.
- A controller without an identity is refused by the core (T-46). A test that runs one (a poll, a stream report) sets `unenrolledControllers = true` after its imports, as `tstream.nim` does; a core started by a script sets `CINIM_UNENROLLED_CONTROLLERS=on`.
- `sizeOf` is `sizeof` and `tOk` is `tok` for Nim (identifiers are style-insensitive after the first letter): a proc called `sizeOf` and a constant `tok` next to a `tOk` break in strange ways (`objectSize` in the store). `removeDir` removes what is in the directory too: to remove only an empty one use `rmdir` (the store's `deleteObject` did once, caught by its test).
- A `quit` inside an `if` block placed before the closures of a long proc (`runMode` in `src/conductor/main.nim`) made the closure environment nil and the run process died with SIGSEGV at the next `replay.execute`, with no trace below the proc: put such a branch in a proc of its own (`checkMode`). gdb on the binary built with `--debugger:native`, fed the pipe frames from a file, finds it.
- A process started with `startProcess` and a pipe (`poStdErrToStdOut`) that nobody reads stops when the pipe is full (64 KiB): a Caddy node did, after about 200 requests, because it logs a line for each (see the next point). Redirect the log of a node to a file (`sh -c "exec caddy ... > file 2>&1"`, as `tstorehttp.nim` does).
- GuildenStern follows a reply with an **empty body** with a stray CRLF; Caddy logs an "unsolicited response on an idle channel" for each. Reply with a body that is not empty (`reply(Http200, "ok")`), as the route `store-auth` does.
- A `ref` shared by several threads crashes (ORC counts references without atomics): every thread makes its own `HttpMirror` (the module makes the backend for each request). A benchmark that shared one died in the middle of a run with SIGSEGV.
- Before a run of `tstorehttp`/`tstorehttprepair`/`tstorageproc` that was killed, `pgrep -x caddy-store` and `pgrep -x storage` and kill what is left: the new nodes cannot bind, and the test would talk to the old ones (it now refuses to start when a port is in use).
- The nodes of a new `dav` store ask the module (`forward_auth`) for their token **before the store is saved**, because the module tries the settings first: `service.nim` keeps the token of the store being tried for a minute (`tryingSecret`). A change to the order of "try, then keep" breaks the first `PUT /v1/admin/stores/...` of every Caddy store.
- Do not build the Caddy image (Go, xcaddy) with Kaniko on the TESTING cluster while rqlite shares the worker: the build starved the node and two nodes went `NotReady`. Build `build/caddy-store` on the workstation (`tools/store/build-caddy.sh`), `docker build` a `FROM caddy` image with it and `skopeo copy --dest-tls-verify=false docker-daemon:<image> docker://<registry>/<image>:<tag>`. The module needs 1 GiB (16 threads x 10 MiB receive buffers): 256 MiB was OOM-killed.
- GuildenStern in `Streaming` mode (the storage module): `getRequest()` asserts `Compact`, so the headers are `http.request[0 ..< http.requestlen]`, read before `receiveStream` (it reuses the buffer); a route that does not read the body must still drain it (`onRequest` does) or the client sees a reset; `getBody` is empty. libcurl: declare `curl_easy_setopt` once with `varargs` (three typed declarations of one C function do not compile), and keep the transfer state in a seq whose addresses do not move.
- A test that imports `core/scheduler`, `core/artifactingest` and `shim/logclient` together finds `StepRef`, `ArtifactRequest`, ... three times (each makes its own copy of the Protobuf types): import the core modules with `from ... import` of the names needed, as `tshimdirect.nim` does.
- The reads of the storage module are streamed (`readStream`, a chunked reply); before that a read was one string in the module, and every thread kept the most it had had (140 MiB after one run with blocks of 4 MiB). A new route that reads must stream too.
- Do not use `.gitignore` patterns that can catch source files (`tests/**/t[!.]*[!.nim]` caught `*.nim.cfg`; there is a negation now).

## Where things are

- Core: `src/core` (API `api.nim`, holds `holds.nim` (runs, groups, the organisation), the audit of variables `varaudit.nim`, the check of a script `preflight.nim` + `checkmail.nim` (the hub side is in `streamhub.nim`: `requestCheck`), the cache `cachestore.nim` + its requests in `artifactingest.nim` (`handleCache`), groups `groups.nim`, variables of the shard / organisation / group `orgvars.nim`, scheduler, log collector, `artifactingest.nim`, `triggers.nim`, `secretvault.nim`, `objectstore.nim` (the rules of an artifact's path and key, the organisation's choice of store) + `storageclient.nim`).
- The storage module (docs/storage-module.md, D-60), a service of its own: `src/storage` (`main.nim` the program, `service.nim` the HTTP API and the repair loop, `registry.nim` the named stores and their settings, `seal.nim` the sealing of their secrets, `repair.nim` the inventory, the repair queue and the lease, `schema.nim` the `storage_*` tables, `s3backend.nim`, `httpstore.nim` + `davclient.nim` + `layout.nim` + `sha.nim` the Caddy mirror, `replicas.nim`, `storeauth.nim` the tokens of the nodes); the seam `src/common/storagebackend.nim` and the token of the core's calls `src/common/storagetoken.nim`; in the core `storageclient.nim` (`RemoteBackend`, `moduleStores`) and `objectstore.nim` (`org_storage`, `storeFor`, `StoreSet`). Tests: `tstorage` (the API without a socket, doubles), `tstorageproc` (the program, real Caddy nodes, the core's client), `tstoreseal`, `tstoreregistry`, `tstorehttp`, `tstorehttprepair`, `tstorelayout`, `thttpstore`, `tstoreauth`. The image `tools/image/Dockerfile.storage`. The module needs `CINIM_RQLITE_URL`, `CINIM_STORAGE_SHARDS` (`001=<secret>`), `CINIM_STORAGE_ADMIN_TOKEN`, `CINIM_STORAGE_SEAL_KEY`; the core `CINIM_STORAGE_URL` and `CINIM_STORAGE_TOKEN`.
- The HTTP store nodes (docs/store.md, D-58): `HttpMirror` (objects as directories of chunks) uses `davclient.nim` (a small async HTTP/1.1 client: `std/httpclient` refuses PROPFIND and MOVE) and answers the nodes' `forward_auth` in `service.nim`; the node is `build/caddy-store` (`tools/store/build-caddy.sh`, the fork `github.com/zystem/caddy-webdav` branch `cinim-store`), the image target `caddy-store`; the chart that runs the nodes is `deploy/charts/cinim-storage`. Tests that need `build/caddy-store` make it if Docker is there (`tstorehttp.nim.cfg` is `-d:ssl`).
- The direct transfer of a shim (docs/storage-module.md, D-61): `shim/directclient.nim` (the HTTP client), `putFile`, `putDirect`, `fetchTo` in `shim/logclient.nim`; in the core `offerDirect`, `checkDirectParts` in `artifactingest.nim`, `grantFor` and `uploadedParts` in `storageclient.nim`, the egress rule in `orgprovision.nim`; in the module `shimDispatch` and `startShimServer` in `storage/service.nim`, `storage_parts`, the grants in `common/storagetoken.nim`. Tests: `tshimdirect` (the whole chain), `tdirectartifact`, `tcache`, `tstorage`, `tstoreseal`, `torgprovision`.
- Run volume (STO-001, D-47): `src/jobcontroller/runvolume.nim` (the claim and what a Pod gets of it), `src/core/runstorage.nim` (which runs' volumes may go), `cicd-shim --prepare-volume` (the init container).
- The drain of what a shim could not deliver (DAT-003, D-27, docs/artifacts.md): the manifest of the artifacts and the log spool are always on the run volume (D-55: it is not optional, and nothing is pulled out of a Pod through `exec`) (`drainDir` in `src/jobcontroller/logic.nim`); `src/core/drains.nim` (table `step_drains`, the order in `PollResponse.drain_steps`, results in `PollRequest.steps_drained`), `src/jobcontroller/drain.nim` (the drain Pod and how it ended), the shim's `--drain` mode (`drainTool` in `src/shim/shim.nim`, `drainLogSpool` and `putFile` in `src/shim/logclient.nim`). The controller's C client returns nothing from `exec` in the TESTING cluster (Kubernetes 1.36): the drain does not use it.
- Shim: `src/shim` (`shim.nim`, `logclient.nim` for every call to the core, `artifacts.nim`, `cachepack.nim` for the archive of a cache). Controller: `src/jobcontroller`. Lua: `src/executor` (sandbox, journal, replay, `bootstrap.lua`, the table of step numbers); the programs that run it: `src/conductor`.
- Conductor (docs/conductors.md, phases 2-3): `src/conductor/main.nim` (supervisor, and the run process with `--run`), `src/common/runpipe.nim`; its side in the core is in `streamhub.nim` and `scheduler.nim` (`leaseForConductor`). Started by hand (`/core conductor-credential <ns> <id>` gives its credential); the controller makes it when the shard has `CINIM_CONDUCTOR_IMAGE` (`src/jobcontroller/conductors.nim`). Build: `nim c -p:src --outdir:build -o:build/conductor src/conductor/main.nim`.
- Charts: `deploy/charts/cinim-shard`, `deploy/charts/cinim-storage` (the storage module with Garage and/or Caddy nodes; its registration scripts are shell inside the templates: extract them from `helm template` and run `sh -n`, or run them with the real busybox against a stand-in, as phase 3 did), `deploy/charts/cinim-router`. Examples: `deploy/examples` (the key-service emulator, build Pods, self-build, the soak harness).
- Ports of the core: 18081 API, 19742 step report, 19743 log ingest, 19744 artifact ingest, 19745 the push channel of the controllers (docs/conductors.md section 12).
