# Working on CiNim (notes for a coding session)

Read `README.md` first (what works, the structure, the build), then `docs/specification.md` for a requirement you touch (IDs like `PIP-012`, `DAT-003`, decisions `D-xx`).

## Rules of the project

- Tests first; the name of a test contains the ID of the requirement it verifies. All unit, protocol contract (`tests/contract`: `tproto_compat` needs `buf`, which the test image has and the pipeline requires with `CINIM_REQUIRE_BUF=1`; elsewhere it skips) and integration tests, in parallel, about 2 minutes: `tools/test/run.sh` (`-j 8` workers by default, more gains little; every worker has its own rqlite in a Docker container, made new at each run;
  `-u`/`-i` only unit (and contract)/integration; `tm1skeleton` needs the Kubernetes client and a cluster: name it on the command line). `nimble test` runs the unit tests in turn (about 5 minutes). Run a single file with
  `nim c -r --hints:off --warnings:off --outdir:build/tests tests/unit/<file>.nim`.
- `tools/test/lint.sh` (POSIX sh) checks what no test compiles: shellcheck on the scripts, hadolint on the Dockerfiles (`.hadolint.yaml` says what is not followed), `helm lint --strict` and `helm template` on the charts, kubeconform on what was rendered. The pipeline runs its four parts side by side with the tests, each in the image of its tool (`LINT` parameter, `.ci/pipeline.lua`); locally `LINT_REQUIRE=1 tools/test/lint.sh` fails on a tool that is missing. `tests/unit/trepository.nim` keeps the rules of this file that a grep can check (`newHttpServer`, `pkill -f`, `declared`, tokens, the owner's private words from `~/.config/cinim/private-words`, and that a path in code quotes in a document names a file that exists: what was deleted is in git, not in the text).
- Text in the repository is English. Docs and answers to the owner are in Russian; `docs-tr/` is the owner's gitignored Russian mirror of `docs/` (not in git: update it
  when a doc changes if it exists on your machine).
- The repository holds no private addresses, host names, cluster names or tokens: write "the TESTING cluster" in docs. Real values live in the owner's environment.
- Commit and push only when asked (a stop hook may ask for it). Never `pkill -f` (use `pkill -x name` or a PID). Never ask the owner to paste a token into the chat.
- Dependency updates: Renovate (`renovate.json`, docs/deployment.md "Dependency updates"); a pin that Renovate should move carries `# renovate: datasource=... depName=...` on the line above it (`tests/unit/trepository.nim` checks the comments). Nim is one version everywhere.
- Hooks (`.claude/settings.json`, scripts and their test in `.claude/hooks/`): a `PreToolUse` guard refuses `pkill -f`, `kubectl`/`helm` that name no cluster, the self-truncating file write, and edits of `tests/certs`, the `docs-tr` stamp and `build/`, and asks before `git commit`/`git push`; a `Stop` hook sends the session back once when `docs/` changed and `docs-tr` is stale, when `proto/` changed and `build/nimproto` is older, or when a tracked file became empty. Check them with `.claude/hooks/test-hooks.sh`.
- The records of the log that the shim sends to VictoriaLogs carry the step: its number, `job_id`, `step_id` and `attempt` (D-77, `record` in `src/shim/logspool.nim`; read by `core/logwindow.nim`). When the ids or the structure of jobs and steps change (the widths and the alphabet of ids, the number of a step, a new level of the pipeline), bring those fields, the reader and DAT-001 into line in the same change (the owner, 2026-10-23).
- A new directory of `src/` is a component: add it to `tests/unit/tboundaries.nim` (what it may import, D-81) and to `DEPENDS` in `.ci/pipeline.lua` (what it is built and tested with, D-82; a test keeps the two equal). The pipeline of this repository builds and tests only what changed since the last good run of it (`run.source.base`, told by the platform), decided by `plan` in the script and tested in `tests/unit/tpipelineflow.nim`; a run with no such run (a first one, a script in the request) builds and tests everything.
- The test cluster is for tests: anything may be created and deleted there. The owner decides what is a design change; a doubt about the design is a question, not a guess.
- Report what was checked and what was not. A claim about the code is checked in the code before it is made.

## Building

- Nim 2.2.4 (ORC), `nimble install -d`. System: libsodium (`libsodium-dev`; tests of modules that import `src/common/sodiumaead.nim` link `-lsodium`), a static nghttp2 1.61 or later in `/opt/nghttp2` (nimgrpc links it; `-d:nghttp2Prefix=<dir>` for another place; the image `Dockerfile.deps` and `Dockerfile.test` build it), libpcre (the UI templates).
- `tests/unit/thsmgate_tls.nim.cfg` (`-d:ssl`) belongs to the TLS test of the key service; `thsmgate.nim`, `thsmgate_tls.nim` and `integration/tkeyservice.nim` run the real hsmgate: the test image has it (built from the tag `HSMGATE_REF` of `Dockerfile.test`, `HSMGATE_BIN` is set; a new hsmgate is a change of that ARG, and the run says whether the core still speaks with it), and they are skipped on a machine without `HSMGATE_BIN=<path>` (`go build -o /tmp/hsmgate ./cmd/hsmgate` in `~/github/hsmgate`; the TLS one needs the `openssl` command for `tests/support/mkcerts.sh`).
- The shim has two builds: without `-d:shimLogging` (no gRPC client, what the unit tests use) and with it (the real one). Check both: `nim check -d:shimLogging src/shim/shim.nim` and without.
- The job controller needs the Kubernetes C client (`-d:k8sPrefix=...`); without it use `nim check -d:k8sPrefix=/opt/k8s src/jobcontroller/main.nim` to type-check only.
- After a change to `proto/`: `tools/proto/nim_flatten.sh build/nimproto` (it also makes `build/nimproto/protos.nim`, the Nim types of all the messages, which the modules of `src/` import and export; the macro `import_proto3` took 7 s in every compile of a test and made a copy of the types in every module that used it, so it is not used there any more; the module is kept by the hash of the proto files). A new type of the messages that has the name of one of the project's own types is ambiguous where both are imported: write `protos.GateState(...)`.
- Quick iterations: `REGISTRY=<host> tools/image/build-local.sh <tag> core storage ...` builds on the workstation with a persistent Nim cache and pushes with `skopeo` (seconds after a change; docs/deployment.md). Releases and anything that must not depend on this machine: the build Pod.
- Images are built in the cluster with `REGISTRY=<host:port as the Pods reach it> TAG=<tag> tools/image/kaniko-build.sh` (both images; Kaniko runs as a build Pod, it needs a few minutes; the script's own
  `kubectl logs -f` may time out before the build ends: wait for the Pod `kaniko-images` in `cinim-build` to be `Succeeded`). Roll out: `helm upgrade` with the new `image.tag` (the controller and conductor images follow it); nothing else by hand (D-62: the core replaces the controller Pod of every organisation when its image changes, and drains and replaces a conductor of another image).

## Things that cost time (do not repeat)

- **ASan on a machine with `vm.mmap_rnd_bits` above 28 crashes at start now and then** (`AddressSanitizer:DEADLYSIGNAL` printed for ever, 12 of 30 starts in a test; the Ubuntu 24.04 kernel has 32, gcc 12 images are hit): `tools/test/check-mmap-rnd.sh` checks it and fails with the cure (`sysctl vm.mmap_rnd_bits=28` as root); `nimble testsan` and `tools/soak/run72.sh` run it first. A runner of ASan of your own calls it too, and repeats a start that crashed until it has the clean runs it needs. `CINIM_TEST_ASAN=1 tools/test/run.sh <files>` builds the files with ASan on the system allocator (`-d:useMalloc`) and does both; the pipeline parameter `ASAN` runs the files of the push channel that way (`tests/unit/tstream`, `tests/integration/tstream`, `tconductorhub`), and a schedule trigger with `ASAN=true` makes it a nightly run. A thread that is joined must not be reading a channel that `close` frees: `shutdown` first (nimgrpc 0.2.2 and later), or cancel the call as `src/common/stream.nim` does.
- **A database left on a test port is talked to instead of a fresh one.** A scratch container on 24601 (weeks old, the schema of another day) served the worker 1 of `tools/test/run.sh` and made files fail or pass for no reason of their own (`no such column`, a unique index that no longer exists). `run.sh` now stops with exit 2 when a port of a worker (24600+N, 24700+N) is in use: stop what holds it (`docker ps`, `ss -ltnp`), do not keep a scratch database on those ports. The same holds everywhere something is started on a port it chose: a test calls `requireFreePort` (`tests/support/freeport.nim`; the stand-ins of `tests/support` do it themselves and no longer `discard` the result of `start`), a script sources `tools/test/portfree.sh` (`require_free_port`), and `trepository` fails a test that binds a port and does not ask. A new test or script that takes a port asks first.
- A segmentation fault with no trace in the shim or a thread: iterate a possibly-`nil` `JsonNode` only through `.elems` after a `kind` check (`n{"key"}.kind` is a crash too when the key is missing: test `not n.isNil` first, as `isKind` in `src/ui/app.nim`; a test whose fake body always has every key does not see it). `for x in items(node)` always picks the iterator of `std/json`,
  whatever a function of your own with that name does. Build with `--stackTrace:on --lineTrace:on` and run the binary locally; it shows the line.
- `declared` is a magic of Nim: do not name a proc or a constant so. `func` cannot call `parseJson` (side effects): use `proc`.
- `std/net` `recv(pointer, size, timeout)` insists on all `size` bytes even on an unbuffered socket: wait with `poll` and `recv` without a timeout (`src/shim/artifacts.nim: readSome`).
- A string made in one thread and freed in another crashes tests that use threads: use fixed arrays for what crosses.
- Tools that write a file from itself (`open(p,'w').write(open(p).read())`) truncate it. Edit with a script that reads first, check `git diff --stat` before a commit.
- Integration tests (`CINIM_RQLITE_URL`) need a scratch rqlite; `tools/test/run.sh` starts them in Docker (RAM-backed, faster than a port-forward). By hand: `docker run -d -p 127.0.0.1:24600:4001 --tmpfs /rqlite/file:rw,size=512m,mode=1777 rqlite/rqlite -fk -disco-mode=`. Against a cluster: one node, 1Gi (`helm install rqlite rqlite/rqlite --version 2.0.0 --set replicaCount=1,persistence.size=1Gi`) and a port-forward to the Pod (`pod/rqlite-0 24555:4001`), not to `svc/rqlite`: through the Service the requests hang. A test that makes tables of its own gives them its own names (`bench_...`): the schema's names belong to the other tests.
- The kube API proxy eats the `Authorization` header: reach the core API through a port-forward or an Ingress.
- The controller does not use Kubernetes `exec` (its C client returned nothing in the TESTING cluster, Kubernetes 1.36; D-55); what a step Pod could not deliver is on the run volume and a drain Pod delivers it.
- The controller of an organisation is a Pod of the core (D-62): it is deleted and made again by the core when it is not enrolled, silent, of another generation or of another image. A used identity is rotated when the next Pod is made: to lock out a credential, delete the controller Pod (there is no rotate call).
- Make every HTTP server with `newService` of `src/common/httpsrv.nim`, not with `newHttpServer`. GuildenStern 9.0.1 looked for `content-length: ` in the whole receive buffer of a thread, found the header of an earlier POST behind the end of a shorter request and closed the connection (a third of the connections after a few dozen POSTs; `kubectl port-forward` died at the first); the fix is ours, GuildenStern#38, in 9.0.2 (`cinim.nimble` asks for it; with 9.0.1 installed `tests/integration/thttp.nim` fails). The default reading knows only the spellings `content-length: ` and `Content-Length: `.
- A controller without an identity is refused by the core (T-46). A test that runs one (a poll, a stream report) sets `unenrolledControllers = true` after its imports, as `tstream.nim` does; a core started by a script sets `CINIM_UNENROLLED_CONTROLLERS=on`.
- `sizeOf` is `sizeof` and `tOk` is `tok` for Nim (identifiers are style-insensitive after the first letter): a proc called `sizeOf` and a constant `tok` next to a `tOk` break in strange ways (`objectSize` in the store). `removeDir` removes what is in the directory too: to remove only an empty one use `rmdir` (the store's `deleteObject` did once, caught by its test).
- A `quit` inside an `if` block placed before the closures of a long proc (`runMode` in `src/conductor/main.nim`) made the closure environment nil and the run process died with SIGSEGV at the next `replay.execute`, with no trace below the proc: put such a branch in a proc of its own (`checkMode`). gdb on the binary built with `--debugger:native`, fed the pipe frames from a file, finds it.
- A process started with `startProcess` and a pipe (`poStdErrToStdOut`) that nobody reads stops when the pipe is full (64 KiB): a Caddy node did, after about 200 requests, because it logs a line for each (see the next point). Redirect the log of a node to a file (`sh -c "exec caddy ... > file 2>&1"`, as `tstorehttp.nim` does).
- GuildenStern follows a reply with an **empty body** with a stray CRLF; Caddy logs an "unsolicited response on an idle channel" for each. Reply with a body that is not empty (`reply(Http200, "ok")`), as the route `store-auth` does.
- A `ref` shared by several threads crashes (ORC counts references without atomics): every thread makes its own `HttpMirror` (the module makes the backend for each request). A benchmark that shared one died in the middle of a run with SIGSEGV.
- Before a run of `tstorehttp`/`tstorehttprepair`/`tstorageproc` that was killed, `pgrep -x caddy-store` and `pgrep -x storage` and kill what is left: the new nodes cannot bind, and the test would talk to the old ones (it now refuses to start when a port is in use).
- The nodes of a new `dav` store ask the module (`forward_auth`) for their token **before the store is saved**, because the module tries the settings first: `service.nim` keeps the token of the store being tried for a minute (`tryingSecret`). A change to the order of "try, then keep" breaks the first `PUT /v1/admin/stores/...` of every Caddy store.
- Do not build the Caddy image (Go, xcaddy) with Kaniko on the TESTING cluster while rqlite shares the worker: the build starved the node and two nodes went `NotReady`. Build `build/caddy-store` on the workstation (`tools/store/build-caddy.sh`), `docker build` a `FROM caddy` image with it and `skopeo copy --dest-tls-verify=false docker-daemon:<image> docker://<registry>/<image>:<tag>`. The module needs 1 GiB (16 threads x 10 MiB receive buffers): 256 MiB was OOM-killed.
- GuildenStern in `Streaming` mode (the storage module): `getRequest()` asserts `Compact`, so the headers are `http.request[0 ..< http.requestlen]`, read before `receiveStream` (it reuses the buffer); a route that does not read the body must still drain it (`onRequest` does) or the client sees a reset; `getBody` is empty. libcurl: declare `curl_easy_setopt` once with `varargs` (three typed declarations of one C function do not compile), and keep the transfer state in a seq whose addresses do not move.
- The reads of the storage module are streamed (`readStream`, a chunked reply); before that a read was one string in the module, and every thread kept the most it had had (140 MiB after one run with blocks of 4 MiB). A new route that reads must stream too.
- One test file that hangs held the pool of `tools/test/run.sh` for the two hours of the step's limit, with no word of which file it was (the results of the others had been printed, the summary line never was): a run of the pipeline died of the limit (exit 124) with 169 files `ok`. `run.sh` now kills a file after `CINIM_TEST_FILE_TIMEOUT` (900 s, compiling included) and reports it as `FAIL ... TIMED OUT`. A suspect is `unit/thsmgate_tls`, the only file that did not report in that run: in the test image it runs the real hsmgate (`HSMGATE_BIN`), here it is skipped.

- Do not use `.gitignore` patterns that can catch source files (`tests/**/t[!.]*[!.nim]` caught `*.nim.cfg`; there is a negation now).

- **Nim 2.2.6 writes a wrong request line for HTTPS through an HTTP proxy** (`GET host:port/path` inside the CONNECT tunnel; 2.2.4 writes `GET /path`), a server answers 400. The tag `nimlang/nim:2.2.4-alpine` held 2.2.6 (so the images of the core were built with it while the workstation had 2.2.4); since 2026-10-20 the images are built with 2.2.12 on `ghcr.io/zystem/nim:2.2.12-alpine` (github.com/zystem/nim-alpine: the official Alpine images stopped at 2.2.6; the tests' image is the official Debian `nimlang/nim:2.2.12`) and the workstation has 2.2.12 too: keep them equal, a test that passes here can fail in the cluster otherwise. `core/transitclient.nim` refuses to compile with 2.2.6 (a `static` assert); `tests/unit/thsmgate_tls.nim` runs the real hsmgate through a stand-in proxy, or through a real one with `HSMGATE_TEST_PROXY=http://127.0.0.1:18888` (tinyproxy with `ConnectPort 18942`). Check what a client sends, with the compiler of the image, before trusting a test of a path that std/httpclient builds.
- Any failure to open the master key **at the start of the core** is fatal (a key that is not the one that sealed the database, a service that refuses the core, a proxy's page, a damaged setting, a service that does not answer): `vaultsetup.nim` writes `core: FATAL: ...` and the process exits with 1 (`_exit`: `quit` from a thread crashed with 139 and hid the message), so that Kubernetes shows CrashLoopBackOff; the last log lines are the termination message (`terminationMessagePolicy: FallbackToLogsOnError`, `kubectl describe pod`). So is a key service that does not answer at the start (a restart of hsmgate, the machine of the card): any failure at the start ends the core, and Kubernetes' backoff is the retry; only a core that is already running waits for a key service that goes away. The Deployment is `Recreate`: a core that crashes at the start takes the old one's place, there is no old one left running.

- **A job of the profile `build` or `deploy` is refused unless its project (or a group above it) lists the profile in `allowed_profiles`, and `deploy` unless the run is on a protected ref** (D-86). After a rollout of this version the self-build project needs `PUT /api/v1/organizations/<org>/projects/<path>/settings` with `{"allowed_profiles": ["build", "deploy"], "protected_refs": ["main"]}` (an administrator has `profile.grant` and `ref.protect`), or the jobs of the next run fail with "not allowed for this project". The poll trigger's ref `main` is what makes its runs trusted; a run started by a bare commit hash is never trusted. Secrets can be set on a group or a project (`.../projects/<path>/secrets/<NAME>`, `protected: true` for the trusted runs only).
